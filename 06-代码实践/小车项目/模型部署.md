## 〇、大白话总览

### "训练 30% / 部署 70%"为什么？

```
训练环境: A100 显卡，随便跑，不在乎延迟
小车环境: Jetson 小卡，电池供电，慢了就撞墙
```

> [!note] 打个比方
> 训练像"在实验室里跑车"（条件好随便测）；部署像"把赛车塞进街道跑比赛"（体积/油耗/反应全要符合街头条件）。**"模型能跑（训练）≠ 模型能用（部署）"**——部署要解决"算力差 100 倍 + 延迟必须 <50ms"两个硬约束。

### 部署的四板斧（先记住）

```
① 换小模型:   大模型 → 轻量模型（YOLOv8n 代替大网络）
② 蒸馏:       大模型教小模型（精度损失小）
③ 量化:       FP32 → FP16/INT8（快 2-4 倍）
④ 剪枝:       删不重要的权重/通道（更小更快）
```

## 一、训练 vs 部署的差距

| | 训练环境 | 小车部署环境 |
|------|------|------|
| **硬件** | A100 / 4090 | Jetson Nano / Orin / Raspberry Pi |
| **算力** | 300+ TFLOPS | 0.5 ~ 40 TOPs |
| **内存** | 24GB+ VRAM | 4~8GB 共享内存 |
| **功耗** | 不关心 | 必须 <15W（电池供电） |
| **精度** | FP32 | FP16 / INT8 |
| **框架** | PyTorch | TensorRT / ONNX Runtime / TFLite |
| **延迟要求** | 不关心 | <50ms（否则撞墙） |

> [!warning] 六大差距的"致命性"排序（面试谈资）
> **算力差 100 倍**（300 TFLOPS → 3 TOPs）是根源；**功耗 <15W** 是硬约束（电池）；**延迟 <50ms** 是生死线（车在动，反应慢就撞）；精度/框架/内存都是"跟着前三者走"的衍生问题。**"部署 = 在'算力-功耗-延迟'三角里找最优"**——和 [[模型部署与延迟优化]] 的延迟预算完全一致。

## 二、模型轻量化策略

### 策略 1：直接用小模型

| 模型 | 参数量 | 推理速度(Jetson Nano) | 精度 | 用途 |
|------|:--:|:--:|:--:|------|
| MobileNetV3-Small | 2.5M | ~8ms | 67% top-1 | 分类/特征提取 |
| EfficientNet-B0 | 5.3M | ~15ms | 77% | 分类 |
| YOLOv5n | 1.9M | ~30ms | 28% mAP | 目标检测 |
| YOLOv8n | 3.2M | ~35ms | 37% mAP | 目标检测 |
| NanoDet-Plus | 1.1M | ~20ms | 27% mAP | 目标检测 |
| ERFNet | 2.1M | ~25ms | 72% mIoU | 语义分割（车道线） |

> [!note] 读表的方法："n 后缀 = nano 轻量版"
> **YOLOv5n/YOLOv8n 的"n"= nano（轻量版）**——同系列还有 s/m/l/x（越大越准越慢）。**"选型 = 精度需求 × 延迟预算"**（Jetson Nano 上 30-35ms 满足 <50ms 预算）：检测选 YOLOv8n（37% mAP）、车道线选 ERFNet（72% mIoU）——**"任务 → 模型家族 → 大小档位"三层选型**。

### 策略 2：知识蒸馏

用大模型（Teacher）教小模型（Student），小模型也能有接近大模型的精度。

```
Teacher: ResNet-50 (25M) — 精度 80%, 推理 80ms
    ↓ 蒸馏（用 Teacher 的 soft label 训练 Student）
Student: MobileNetV3 (2.5M) — 精度 76%, 推理 8ms
```

> [!note] 蒸馏的直觉："老师教的不只是答案，还有思路"
> 大模型（老师）输出**软标签**（"95% 是车，3% 是卡车"——含不确定性信息），小模型（学生）学软标签——**比只学硬标签（"是车"）信息量大**。效果：**2.5M 小模型拿到 76% 精度（大模型 80% 的 95%）**——"压缩 10 倍参数，只丢 4 个点"（[[模型训练与微调]] 的知识蒸馏在部署侧的应用）。

### 策略 3：量化

| 精度 | 模型大小 | 推理速度 | 精度损失 | 适用 |
|:--:|:--:|:--:|:--:|------|
| FP32 | 1× | 1× | — | 训练 |
| FP16 | 0.5× | 1.5-2× | <0.5% | Jetson (推荐) |
| INT8 | 0.25× | 2-4× | 1-3% | Jetson (激进) |
| INT4 | 0.125× | 3-5× | 3-8% | 极端场景 |

> [!warning] 量化的"三步走"（面试谈资）
> **FP16 先行（无损白赚 1.5-2 倍）→ INT8（有损但快 2-4 倍）→ INT4（极端）**。**小车默认 FP16**（Jetson 对 FP16 优化好）；**INT8 需要校准数据集**（不能直接转，否则精度崩——[[模型部署与延迟优化]] 的 INT8 逐层分析在小车上同样适用）。**"先 FP16 白赚，再考虑 INT8"是部署的第一课。**

### 策略 4：剪枝

移除不重要的权重/通道 → 模型更小更快。

> [!note] 剪枝的直觉："删掉不重要的神经元"
> 训练后有些权重接近 0（没用）→ 删掉它们（结构化剪枝删整个通道）→ 模型变小变快，精度略降。**"蒸馏/量化/剪枝可叠加"**（先蒸馏变小 → 再量化变快 → 再剪枝更小）——**"组合拳"是部署的常态**（[[模型基础知识补充]] 的"组合拳"思想）。

## 三、PyTorch → ONNX

### 导出

```python
import torch

# 假设你有一个训练好的模型
model = MyLaneDetectionModel()
model.load_state_dict(torch.load('best_model.pth'))
model.eval()

# 导出 ONNX
dummy_input = torch.randn(1, 3, 224, 224)  # 批次大小1很重要
torch.onnx.export(
    model,
    dummy_input,
    'model.onnx',
    input_names=['input'],
    output_names=['output'],
    dynamic_axes={'input': {0: 'batch'}, 'output': {0: 'batch'}},
    opset_version=12  # JetPack 5.x 支持 opset 12-17
)

# 验证 ONNX 模型
import onnx
onnx_model = onnx.load('model.onnx')
onnx.checker.check_model(onnx_model)
print("ONNX export OK")
```

### ONNX Runtime 推理（CPU / 轻量 GPU）

```python
import onnxruntime as ort
import numpy as np

# 创建推理会话
session = ort.InferenceSession(
    'model.onnx',
    providers=['CUDAExecutionProvider', 'CPUExecutionProvider']  # GPU 优先
)

# 推理
input_data = np.random.randn(1, 3, 224, 224).astype(np.float32)
outputs = session.run(['output'], {'input': input_data})
```

> [!warning] 导出 ONNX 的两个"必须"（新手最容易翻车）
> ① **`model.eval()`**——不转 eval 模式，BN/Dropout 行为不同，导出的模型推理结果和训练不一致（[[计算机视觉基础]] 的 BN 陷阱）；② **`dummy_input` 形状**——"批次大小 1 很重要"（`dynamic_axes` 可加可不加，固定 batch=1 最简单）。**"导出前先验证（onnx.checker）"是防坑第一步。**

## 四、TensorRT（Jetson 核心技能）

TensorRT 是 NVIDIA 的推理优化引擎，在 Jetson 上必备：

### FP16 优化

```python
import tensorrt as trt
import pycuda.driver as cuda
import pycuda.autoinit

# === 方法 1: trtexec (命令行，最简单) ===
# trtexec --onnx=model.onnx \
#         --fp16 \
#         --saveEngine=model_fp16.trt \
#         --workspace=2048

# === 方法 2: Python API ===
def build_engine(onnx_path, fp16=True):
    logger = trt.Logger(trt.Logger.WARNING)
    builder = trt.Builder(logger)
    network = builder.create_network(
        1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH))
    parser = trt.OnnxParser(network, logger)
    
    with open(onnx_path, 'rb') as f:
        parser.parse(f.read())
    
    config = builder.create_builder_config()
    config.max_workspace_size = 1 << 30  # 1GB
    if fp16:
        config.set_flag(trt.BuilderFlag.FP16)
    
    engine = builder.build_engine(network, config)
    return engine

# 保存 engine
engine = build_engine('model.onnx', fp16=True)
with open('model_fp16.trt', 'wb') as f:
    f.write(engine.serialize())
```

### TensorRT 推理

```python
class TRTInference:
    def __init__(self, engine_path):
        self.logger = trt.Logger(trt.Logger.WARNING)
        with open(engine_path, 'rb') as f, trt.Runtime(self.logger) as runtime:
            self.engine = runtime.deserialize_cuda_engine(f.read())
        self.context = self.engine.create_execution_context()
        
        # 分配显存
        self.inputs, self.outputs, self.bindings = [], [], []
        for binding in self.engine:
            shape = self.engine.get_binding_shape(binding)
            size = trt.volume(shape) * self.engine.get_binding_dtype(binding).itemsize
            d_mem = cuda.mem_alloc(size)
            self.bindings.append(int(d_mem))
            if self.engine.binding_is_input(binding):
                self.inputs.append({'name': binding, 'device': d_mem, 'shape': shape})
            else:
                self.outputs.append({'name': binding, 'device': d_mem, 'shape': shape,
                                     'host': cuda.pagelocked_empty(shape, dtype=np.float32)})
    
    def infer(self, input_data):
        # 拷贝输入到 GPU
        cuda.memcpy_htod(self.inputs[0]['device'], input_data.ravel())
        
        # 推理
        self.context.execute_v2(self.bindings)
        
        # 拷贝输出到 CPU
        for o in self.outputs:
            cuda.memcpy_dtoh(o['host'], o['device'])
        
        return [o['host'].reshape(o['shape']) for o in self.outputs]

# 使用
trt_model = TRTInference('model_fp16.trt')
result = trt_model.infer(np.random.randn(1, 3, 224, 224).astype(np.float32))
```

### 性能对比（Jetson Nano 实测参考值）

| 模型格式 | ResNet-18 | YOLOv5n |
|----------|:--:|:--:|
| PyTorch FP32 | 45ms | 120ms |
| ONNX FP32 | 35ms | 90ms |
| TensorRT FP32 | 18ms | 55ms |
| **TensorRT FP16** | **10ms** | **30ms** |

> [!warning] 读性能表的"三个跳变"（面试谈资）
> **PyTorch→ONNX（-25%）：去掉 Python 开销；ONNX→TRT FP32（-40%）：算子融合/自动调优；TRT FP16（-45%）：半精度**。**总计 PyTorch → TRT FP16 快 4-5 倍**（45ms→10ms、120ms→30ms）。**"每一跳都来自一个明确的技术"**（框架开销/引擎优化/精度降级）——这就是 [[模型部署与延迟优化]] 的"先测后砍"在实数据上的体现。

## 五、端到端推理管线

```python
class CarInferencePipeline:
    """
    完整的推理管线：图像 → 模型 → 控制指令
    """
    def __init__(self, model_path, serial_port):
        self.model = TRTInference(model_path)
        self.ser = serial.Serial(serial_port, 115200)
        self.cap = cv2.VideoCapture(0)
        
        # 预处理参数（必须和训练时一致！）
        self.mean = np.array([0.485, 0.456, 0.406])
        self.std = np.array([0.229, 0.224, 0.225])
        self.input_size = (224, 224)
    
    def preprocess(self, frame):
        """与训练时保持完全一致的预处理"""
        img = cv2.resize(frame, self.input_size)
        img = cv2.cvtColor(img, cv2.COLOR_BGR2RGB)
        img = img.astype(np.float32) / 255.0
        img = (img - self.mean) / self.std
        img = np.transpose(img, (2, 0, 1))  # HWC → CHW
        return np.expand_dims(img, axis=0)    # → NCHW
    
    def postprocess(self, output):
        """模型输出 → 控制指令"""
        # 假设模型输出 [steering, throttle]
        steering = float(output[0][0])
        throttle = float(output[0][1])
        
        # 映射到实际范围
        steer_angle = int(90 + steering * 40)  # 90±40
        throttle_pwm = int(throttle * 150 + 105)  # 105~255
        
        return max(50, min(130, steer_angle)), max(0, min(255, throttle_pwm))
    
    def run(self):
        try:
            while True:
                ret, frame = self.cap.read()
                if not ret: continue
                
                # 推理
                tensor = self.preprocess(frame)
                output = self.model.infer(tensor)
                
                # 控制
                steer, throttle = self.postprocess(output)
                cmd = f"S{steer}T{throttle}\n"
                self.ser.write(cmd.encode())
                
                # 监控延迟
                t = time.time()
                # print(f"Inference: {(time.time()-t)*1000:.1f}ms")
        finally:
            motor_stop()
```

> [!note] 管线 = "预处理 → 推理 → 后处理"三段（全库串联）
> **预处理**（resize/归一化，**必须和训练一致**）→ **推理**（TRT）→ **后处理**（模型输出 → S/T 控制指令）→ 串口发给 Arduino（[[底盘与电机控制]] 的协议）——**这就是 [[端到端小车实战]] 的"部署版"**：模型在 Jetson 上跑，控制指令走串口。**"管线把模型和硬件接起来"——小车主线所有笔记在这里汇合。**

## 六、常见部署坑

| 坑 | 现象 | 解决 |
|----|------|------|
| **预处理不一致** | 训练正常，部署完全不对 | 导出预处理为 ONNX 的一部分，或用脚本确保一致性 |
| **RGB/BGR 搞反** | 检测结果混乱 | OpenCV 默认 BGR，训练通常是 RGB |
| **动态 batch size** | TensorRT 报错 | 导出 ONNX 时固定 batch=1 |
| **算子不支持** | ONNX→TensorRT 转换失败 | 检查 opset 版本，替换不支持的算子 |
| **精度损失太大** | INT8 推理不准 | 先用 FP16；INT8 需要校准数据集 |
| **Jetson 过热降频** | 推理忽快忽慢 | 加强散热，降低功耗模式 |

> [!warning] 六大坑的"两个头号杀手"（面试/实战重点）
> **① 预处理不一致**——训练时归一化 (mean/std) 和部署时不一样 → 模型"看到"的分布变了 → 结果全错（**"预处理必须和训练逐字节一致"**）；**② RGB/BGR 搞反**——OpenCV 读图默认 BGR，训练库默认 RGB → 颜色通道对调 → 检测混乱。**"前处理错 = 全错"**（数据侧的错误最致命，[[数据挖掘与自动标注]] 的"垃圾进垃圾出"在部署同样成立）。

## 七、常见误区速查

> [!warning] 部署最常踩的坑
> 1. **训练完直接塞小车**——训练环境和小车环境差 100 倍算力；**部署 = 轻量化 + 引擎优化**（不是"拷过去就能跑"）。
> 2. **一上来就 INT8**——INT8 需要校准数据集，直接用精度崩；**FP16 先行（无损白赚）**。
> 3. **忽略预处理一致性**——训练/部署预处理不一致 = 模型看到的分布变了 = 结果全错（头号杀手）。
> 4. **忘记 model.eval() 再导出**——BN/Dropout 行为不同，导出的 ONNX 结果不一致。
> 5. **忽略 Jetson 散热**——过热降频 = 推理忽快忽慢 = 控制不稳定；**散热是部署的一部分**。
> 6. **只看推理延迟不看端到端**——摄像头采集 + 预处理 + 推理 + 后处理 + 串口的总延迟才是"延迟预算"（[[模型部署与延迟优化]]）。

## ✅ 检验自己（自测题）

> [!question] Q1：训练环境和小车环境的六大差距是什么？哪个是"致命根源"？
> 提示：算力/功耗/延迟。

> [!success]- 参考答案
> 硬件（A100 vs Jetson）、算力（300+ TFLOPS vs 0.5-40 TOPs）、内存（24GB vs 4-8GB）、功耗（不在乎 vs <15W）、精度（FP32 vs FP16/INT8）、框架（PyTorch vs TensorRT）、延迟（不在乎 vs <50ms）。致命根源：**算力差 100 倍**（其他问题都是它的衍生）——部署 = 在"算力-功耗-延迟"三角里找最优。

> [!question] Q2：轻量化四策略是什么？为什么能叠加？
> 提示：小模型/蒸馏/量化/剪枝。

> [!success]- 参考答案
> ① 直接换轻量模型（YOLOv8n 等 n 系）；② 知识蒸馏（大模型软标签教小模型，2.5M 拿到大模型 95% 精度）；③ 量化（FP32→FP16 无损白赚 1.5-2 倍 → INT8 快 2-4 倍有损）；④ 剪枝（删不重要的权重/通道）。可叠加：先蒸馏变小 → 再量化变快 → 再剪枝更小——"组合拳"是部署常态。

> [!question] Q3：PyTorch → ONNX → TensorRT 每一跳为什么变快？
> 提示：框架开销/引擎优化/半精度。

> [!success]- 参考答案
> PyTorch→ONNX（-25%）：去掉 Python 动态开销；ONNX→TRT FP32（-40%）：算子融合（Conv+BN+ReLU 合并）+ kernel 自动调优；TRT FP16（-45%）：半精度计算。总计快 4-5 倍（ResNet-18: 45ms→10ms）。每一跳对应一个明确技术——"先测后砍"的实数据。

> [!question] Q4：导出 ONNX 的两个"必须"是什么？为什么？
> 提示：eval/形状。

> [!success]- 参考答案
> ① `model.eval()`：不转 eval，BN/Dropout 行为不同，导出的模型推理和训练不一致（BN 的 train/eval 陷阱，[[计算机视觉基础]]）；② dummy_input 形状：批次大小 1（固定 batch 最简单，dynamic_axes 可选）——动态 batch 在 TensorRT 易报错。导出后用 onnx.checker 验证是防坑第一步。

> [!question] Q5：部署的"头号杀手"是什么？怎么防？
> 提示：预处理。

> [!success]- 参考答案
> 头号杀手是**预处理不一致**（训练和部署的归一化/resize/RGB-BGR 不同）——模型"看到"的输入分布变了，结果全错（训练正常部署完全不对）。防法：① 预处理参数（mean/std/尺寸）必须和训练逐字节一致；② RGB/BGR 通道顺序（OpenCV BGR vs 训练 RGB）；③ 可把预处理并入 ONNX 图（导出时一起打包）。"前处理错 = 全错"。

## 🛠 动手练习

### 练习 1：导出 + 对比性能（60-90 分钟）

用 [[端到端小车实战]] 的 DAVE-2 模型：
1. `model.eval()` 后导出 ONNX（opset=12）。
2. onnx.checker 验证。
3. 对比 PyTorch vs ONNX Runtime 的推理延迟（各测 100 次取平均）。
4. 记录：ONNX 比 PyTorch 快多少？（预期 20-30%）

> [!tip] 这是"部署三步"的第一步
> 亲手测出"框架开销"，你就理解为什么部署要用 ONNX/TensorRT。**"测延迟要 100 次取平均"**（单次测量噪声大）。

### 练习 2：TensorRT FP16 部署（可选，需 Jetson）

有 Jetson 的话：
1. `trtexec --onnx=model.onnx --fp16 --saveEngine=model_fp16.trt`。
2. 用 TRTInference 类推理。
3. 对比 PyTorch/ONNX/TRT-FP16 三档延迟（应 45/35/10ms 量级）。
4. 验证输出精度（和 PyTorch 输出的误差应 <1%）。

> [!tip] 这是 Jetson 部署的核心技能
> TensorRT 是 NVIDIA 系部署的必备技能（[[模型部署与延迟优化]] 的理论 + 本篇的实战）。**"trtexec 一行命令 + Python 推理类"是标准流程**。

### 练习 3：组装端到端管线（60 分钟）

用第五节 CarInferencePipeline：
1. 接上摄像头和 Arduino（[[底盘与电机控制]] 的串口协议）。
2. 让模型控制小车跑一圈（闭环）。
3. 测"端到端总延迟"（摄像头→控制指令）。
4. 记录：端到端延迟是多少？推理占了多大比例？（[[模型部署与延迟优化]] 的延迟拆解）

> [!tip] 这是小车主线的"毕业考试"
> "图像→模型→控制"全链路跑通 = L3/L4 部署完成。**端到端延迟拆解**（推理 vs 采集 vs 后处理）是量产面试题（[[模型部署与延迟优化]] Q1）的实数据。
