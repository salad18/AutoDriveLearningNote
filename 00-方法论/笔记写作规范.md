# 📝 笔记写作规范（MyKB 方法论）

> 一句话导读：这是本知识库的"写作宪法"——**每篇笔记都按"教学版"结构编写：让一个初学者也能读懂，让读者逐步深入，并有可检验的学习闭环**。所有模板、后续扩展、内容修改都遵循本规范。

## 一、总则：这套方法是什么、为什么

### 1.1 背景

知识库早期笔记是"速查表"风格：概念只有定义、没有解释，适合已经会的人回忆，**不适合初学者学习**。2026-08 起升级为**教学版**：用白话讲透概念、用比喻建立直觉、用推导连接公式、用自测检验掌握。

### 1.2 三条核心原则（判断一切写作决策）

1. **读者是"未来的我"**：写的时候假设读者是一个只有前置知识、没看过这篇的人。能看懂 → 达标；看不懂 → 重写。
2. **先直觉，后公式**：任何概念先讲"它解决什么问题 + 打个比方"，再给公式/代码。公式是直觉的"精确化"，不是起点。
3. **学习闭环**：每篇笔记必须以"能检验"结尾——读者读完要能自测、要能动手、要知道下一步去哪。

> [!warning] 绝对禁止的风格
> - ❌ 只有术语堆砌："Transformer 使用多头注意力机制进行特征提取"（说了等于没说）
> - ❌ 只有结论没有过程："深度估计很难"（为什么难？）
> - ❌ 公式直接扔出来不解释符号："s[u,v,1]ᵀ = K[R|t][X,Y,Z,1]ᵀ"（每个符号是什么？）
> - ❌ 没有链接孤立存在（至少要有"相关笔记"）

## 二、教学版笔记标准结构

> 所有"内容型"笔记（模型、理论、概念、方法论）遵循以下结构。**用 [[通用笔记模板]] 或 [[模型笔记模板]] 起步，按本结构填充。**

### 2.1 Frontmatter（元数据）

```yaml
---
tags: [分类标签, 主题标签]
created: "YYYY-MM-DD"        # 创建日期（必填）
updated: "YYYY-MM-DD"        # 最后更新日期（每次修改必更新）
---
```

- `tags` 至少两个：一个分类（foundation/BEV/end-to-end/training…），一个主题（attention/occupancy/planning…）
- `updated` **每次修改必须更新为当天日期**——这是版本可追溯性的基础

### 2.2 正文结构（按顺序，缺一不可）

```
# 标题

> 一句话导读          ← 用一个比喻或一句话说清"这篇讲什么、为什么值得读"

---

## 🧭 本篇导读          ← 表格：这篇学什么 / 前置知识 / 学完你能 / 预计时间

> [!tip] 学习姿势建议     ← 可选：怎么读这篇（先读哪、注意什么）

---

## 一、正文章节          ← 概念逐个讲透，见第三节"写作原则"
...
（每个概念：为什么需要 → 白话解释 → 比喻 → 逐步推导 → 数字例子）

---

## 常见误区速查          ← > [!warning] callout 列 3-6 个新手最常踩的坑

---

## ✅ 检验自己（自测题）   ← > [!question] 出题 + > [!success]- 折叠答案，见 4.3

---

## 🛠 动手练习           ← 纸笔练习 → 代码练习 → 进阶练习，每个带提示

---

## ➡️ 下一步学什么         ← 按学习路径列出 3-5 篇后续笔记，每篇一句话说明为什么

---

## 相关笔记             ← 双链列表，每条一句话注释
- [[笔记A]] — 为什么相关
```

### 2.3 各区块的写作要点

| 区块 | 要点 | 常见错误 |
|------|------|----------|
| **一句话导读** | 用比喻或大白话一句话说明"这篇是什么" | 写成论文摘要 |
| **🧭 本篇导读** | 前置知识要具体（点名哪篇笔记），"学完你能"写可验证的能力 | 写"了解 XX 概念"这种空话 |
| **正文** | 每个概念按"为什么 → 是什么 → 怎么用"三段；数字例子至少 1 个 | 只有定义没有动机 |
| **常见误区** | 写"新手真的会犯"的错，不是泛泛而谈 | 写"要注意细节"这种废话 |
| **自测题** | 3-6 题，覆盖核心概念；答案必须折叠（见 4.3） | 出题太简单（背定义） |
| **动手练习** | 分级：纸笔（10-20 分钟）→ 代码（30-60 分钟）→ 进阶（可选）；每个练习后跟"做完后自问" | 只有"读论文"没有实操 |
| **下一步** | 指向学习路径上的下一站，说明"为什么读它" | 只列链接不给理由 |

## 三、写作原则（正文怎么写）

### 3.1 七条铁律

1. **一个概念一个比喻**：每个核心概念配一个生活化比喻（查词典、扫描监控、传话游戏…）。比喻放在概念第一次出现处。
2. **逐步推导**：公式/流程拆成步骤，每步配白话解释。公式里**每个符号都要解释**。
3. **数字例子**：能用数字演算的就演算（手算注意力、算投影、算显存）。"算过一遍"和"看过公式"的记忆深度完全不同。
4. **先直觉后公式**：先讲"它在解决什么问题"，再给数学形式。
5. **标注反例**：讲到"为什么需要 X"时，先讲"没有 X 会怎样"。
6. **代码可运行**：代码示例必须完整可跑（含 import、注释），不写伪代码糊弄。
7. **链接有注释**：双链后跟" — 为什么相关"（如 `[[BEVFormer详解]] — Query 机制基础`）。

### 3.2 面向初学者的语言

| ❌ 速查表风格 | ✅ 教学版风格 |
|--------------|--------------|
| 卷积层提取局部特征 | 卷积层用一个"小窗口"在图片上滑动，窗口里的内容决定输出——因为物体是局部的，看局部就够了，不用看全图 |
| 残差连接解决梯度消失 | 残差连接给梯度开了一条"捷径"，让深层网络也能收到回传的梯度——就像高架桥，不堵车了 |
| 深度估计难 | 单目相机里，一个像素对应空间里"一条射线"上的无数个点，距离信息在投影时被数学性地丢掉了——所以只能靠猜 |

### 3.3 篇幅参考（经验值）

| 笔记类型 | 建议篇幅 | 说明 |
|----------|----------|------|
| 基础理论/模型详解 | 400-650 行 | 核心内容型笔记 |
| 概览/全景 | 250-350 行 | 地图型笔记，重结构轻细节 |
| 论文笔记 | 150-250 行 | 重"怎么读"和"和我的关系" |
| 每日记录 | 20-40 行 | 轻量，不套教学版 |
| 大纲 | 100-200 行 | 只写骨架，见 [[后续扩展大纲]] |

## 四、Obsidian 语法规范

### 4.1 Callout 用法（本库统一约定）

| Callout 类型 | 用途 | 示例 |
|--------------|------|------|
| `> [!note]` | 补充说明、直觉解释、背景 | 公式的白话翻译、设计动机 |
| `> [!tip]` | 学习方法、阅读建议、实用技巧 | "读完自问这三个问题" |
| `> [!warning]` | 常见误区、易错点、工程陷阱 | "逐相机独立 flip 是禁止的" |
| `> [!question]` | 自测题 | Q1: ... |
| `> [!success]-` | 自测题答案（**必须折叠**） | `> [!success]- 参考答案` |
| `> [!example]` | 数字例子、案例 | 手算过程 |

> [!warning] 折叠语法必须带 `-`
> 答案用 `> [!success]- 参考答案`（`-` 表示默认折叠）。如果写成 `> [!success] 参考答案`，答案会直接展开，失去"先想再对答案"的效果。

### 4.2 代码块中的链接陷阱

**Obsidian 会把双左方括号开头的内容当成链接解析——包括代码块里的。** 因此：

- 代码/内联代码中出现的嵌套列表（如 `[ [a, b], [c, d] ]`）**必须在两个 `[` 之间加空格**。下面的写法是安全的（Python 合法，Obsidian 不再误判）：

```python
# ✅ 正确写法：两个左方括号之间加空格
matrix = [ [1, 0], [0, 1] ]
# ❌ 错误写法：`[ [1, 0], [0, 1] ]` 写成 `[[1, 0], [0, 1]]` 会被 Obsidian 当链接
```

- 数学矩阵同理：行内公式写 `[ [a, b], [c, d] ]`。
- 每篇笔记写完跑一遍链接检查（见 5.4）。

### 4.3 其他语法约定

- **数学公式**：行内 `$...$`，独立 `$$...$$`。写完检查渲染（Obsidian 需开启 Math 或装 better-mathjax）。
- **mermaid 图**：结构图（数据流、pipeline）优先用 mermaid；画图比文字省 10 倍理解成本。
- **表格**：能用表格对比就对比（路线对比、指标对比、误区列表）。
- **emoji**：区块标题统一前缀（🧭 ✅ 🛠 ➡️），正文不滥用。
- **链接**：笔记内首次提到某概念时链接一次即可，不要重复堆链接。

## 五、更新与维护流程

### 5.1 新建一篇笔记

1. 判断类型 → 复制对应模板（[[模型笔记模板]] / [[通用笔记模板]] / [[论文笔记模板]] / [[日记模板]]）。
2. 按第二节结构填充；不确定的章节先留空标题，不要删除骨架。
3. 在 [[000-知识库地图]] 和 [[学习计划]] 中登记入口。
4. 跑质量检查（5.4）→ Git 提交（5.5）。

### 5.2 扩充/修改一篇旧笔记

1. 先读原笔记，**保留原有技术内容**，只补结构缺失的区块（导读/误区/自测/练习/下一步）。
2. 更新 frontmatter 的 `updated`。
3. 如果修改了章节顺序，检查所有相关链接是否仍指向正确位置。

### 5.3 链接规范

- 指向存在的笔记：用 Obsidian 双链语法（`[` `[` 笔记名 `]` `]`，不带 `.md` 扩展名、不带路径）。
- 指向文件夹：**避免**（Obsidian 文件夹链接不可跳转），改为指向该文件夹中的具体笔记。
- 新增笔记后必须确认：所有引用了它的笔记链接有效。

### 5.4 质量检查清单（提交前必过）

```markdown
□ Frontmatter 完整（tags ≥2，created/updated 有值且 updated 是今天）
□ 有"一句话导读"和"🧭 本篇导读"表格
□ 每个核心概念：为什么 → 白话 → 比喻 → 推导（或数字例子）
□ 有"常见误区速查"（≥3 条）
□ 有"✅ 检验自己"（3-6 题，答案用 > [!success]- 折叠）
□ 有"🛠 动手练习"（至少 1 个纸笔/代码练习）
□ 有"➡️ 下一步学什么"和"相关笔记"（链接带注释）
□ 无代码块链接误判：嵌套列表写成 `[ [a, b] ]` 形式（两个左方括号间有空格）
□ 全部双链指向存在的笔记
```

### 5.5 Git 提交规范

```bash
# 提交信息格式：<类型>: <中文摘要>
# 类型：docs（文档/笔记）| feat（新功能/新笔记）| fix（修复）| refactor（重构）| chore（杂项）

git add -A
git commit -m "docs: 扩充 BEVFormer 详解为教学版，补导读/自测/练习"
git push origin master
```

**要点**：
- 一次提交只做一件事（一篇笔记 = 一个 commit，或一批同主题笔记 = 一个 commit）。
- 提交信息用中文、动词开头、说明"做了什么"，不说"为什么"（理由写在笔记里）。
- 用户要求推送时，commit 后立即 `git push origin master`。
