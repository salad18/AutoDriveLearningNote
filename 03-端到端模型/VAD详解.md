## 〇、大白话总览

### VAD 在做什么？

输入 6 相机图像 → 输出自车轨迹（规划）。和 UniAD 一样是"感知-规划"端到端，但**内部表示完全不同**：

```
UniAD:  图像 → 稠密 BEV 特征 (640K 格子) → 稠密占据 → 规划   [3 FPS]
VAD:    图像 → BEV 特征 → 稀疏矢量 (agent 轨迹+车道线) → 规划  [10+ FPS]
```

### 核心思想（一句话）

**矢量化 = 只存有用的信息。** 驾驶决策不需要"整张地图"，只需要"少数几个关键对象的位置和运动"——所以把稠密表示压缩成稀疏矢量，规划模块的计算量降一个数量级。

> [!note] 打个比方
> UniAD 像"拿着整栋楼的施工图纸找出口"（信息全，但 90% 用不上）；VAD 像"只看出口指示牌"（信息少，但都是要用的）。
> **关键是：开车真的只需要指示牌，不需要施工图纸。** VAD 的贡献就是证明并实现了这一点。

## 一、核心思想（展开版）

**矢量化 = 只存有用的信息。** 一个 BEV 占据栅格 640K 体素中 90% 是"空"或"路面"，VAD 直接将这些信息压缩为稀疏的矢量表示（agent 轨迹、车道线坐标），将 Planner 的计算量降低一个数量级。

```
UniAD:  Image → Dense BEV (640K cells) → Dense Occupancy → Planner  [3 FPS]
VAD:    Image → BEV Features → Vectorized Agents + Lanes → Planner  [10+ FPS]
```

> [!question] 追问: 为什么矢量化就够了？驾驶决策需要哪些信息？

**驾驶决策的最小信息集合：**
1. 周围 agent 的位置和运动 → 矢量化轨迹
2. 车道拓扑 → 矢量化的 lane graph
3. 交通灯状态 → 分类标签
4. 自车状态 → 速度/加速度/朝向

这些全部是**稀疏的**（数量 O(10-100)，而非 640K）→ 矢量化天然匹配。

> [!note] 这个"最小信息集合"分析是 VAD 的理论基础
> 它问了一个没人问过的问题：**"规划到底需要什么信息？"** 答案是 4 类稀疏信息。既然需要的是稀疏信息，稠密表示就是浪费——**"先分析需求，再设计表示"**，这是 VAD 区别于"堆特征"类工作的思维起点。

## 二、架构参数（VAD vs UniAD）

| 参数 | UniAD | VAD | 改进 |
|------|-------|-----|------|
| Backbone | R101/VoV-99 | **R50** | 更轻 |
| Agent 表示 | Track Query (dense) | **Vectorized polyline** | 稀疏 |
| Map 表示 | Map Query (dense) | **Lane graph** | 结构化 |
| Planner 输入 | Dense features | **Sparse vectors** | 高效 |
| FPS | ~3 | **~10** | 3× |
| Planning L2 ↓ | 0.88 | **0.80** | ✓ |
| Collision ↓ | 0.09% | **0.07%** | ✓ |

> [!warning] 这张表最反直觉的点
> VAD 用了**更轻的 Backbone（R50 vs R101）**、**更少的表示（稀疏 vs 稠密）**，结果**规划 L2 和碰撞率都更好**（0.88→0.80，0.09%→0.07%）。
> 这说明：**稠密表示里的大部分信息对规划是"噪声"或"无关"的，砍掉反而让规划更聚焦。** 这也是"稀疏表示 + 显式规划"范式的核心卖点。

## 三、模块详解

### 3.1 Vectorized Motion（Agent 矢量化）

**输出格式**: 每个 agent 的轨迹 = 一系列 (x, y, t) 点，而非 dense heatmap。

```python
# 传统 (UniAD):
# agent_state = dense_heatmap[200, 200] + bbox_regression
# 一个 agent 需要: heatmap peak detection + bbox decode

# VAD:
# agent_traj = [(x_t1, y_t1), (x_t2, y_t2), ..., (x_t6, y_t6)]
# 直接输出 6 个未来时间步的 (x,y) 坐标

# 优势:
# 1. 不需要 dense prediction → 轻量
# 2. 直接消费于 planner → 不需要后处理
# 3. 可解释: 我能看到模型预测的轨迹
```

> [!note] 稠密 vs 矢量的直觉
> - 稠密方式（UniAD）：先预测"每个格子上有没有东西"（热力图），再在热力图上找峰值、解出框——**先铺开再收拢**，中间全是浪费。
> - 矢量方式（VAD）：直接输出"未来每个时刻 (x, y)"——**一步到位，不铺开**。
> 就像查快递：稠密是"翻遍整个仓库找包裹"，矢量是"直接看运单号定位"。

**Agent-Agent 交互**: 用 Self-Attention between agent vectors → 建模交互（如变道、让行）→ 关键创新！

```python
# agent vectors 之间的 Self-Attention
agent_feats = [feat_1, feat_2, ..., feat_N]  # N agents
agent_feats = SelfAttention(agent_feats)
# → 每个 agent 现在知道了其他 agent 的意图
```

> [!note] 为什么"agent 之间的注意力"是关键创新？
> 传统预测模型把每个 agent **独立**预测轨迹（假设别人不动），但真实驾驶里"前车让我，我才变道"——**agent 之间互相影响**。VAD 让所有 agent 的矢量特征做 Self-Attention：**每个 agent 的预测都参考了其他 agent 的意图**，交互建模从"外部规则"变成"网络内部机制"（类似 [[UniAD详解]] 里 Track Query 的互相排斥，但作用在预测上）。

### 3.2 Vectorized Map（车道矢量化）

类似 MapTR，将车道线表示为 polyline（折线）：

```
车道 Centerline: [(x₁,y₁), (x₂,y₂), ..., (x₂₀,y₂₀)]  (20 points sampled)
车道 Divider:    [(x₁,y₁), (x₂,y₂), ...]
人行横道:        polygon vertices [(x₁,y₁), (x₂,y₂), (x₃,y₃), (x₄,y₄)]
```

**为什么用 polyline 而不像 HD Map 用参数化曲线？**
- Polyline 足够灵活（任何形状）
- 直接输出有序点集 → 不需要拟合
- 和 Transformer decoder 天然匹配（each point = a query）

> [!note] 车道为什么也要"矢量"？
> 规划需要知道"哪条道能走、怎么连到下一条道"（车道拓扑）。车道线本质是**线**，不是"格子"——用稠密格子表示线是巨大的浪费。**把线表示为折线点集，既保真又省量**，而且每个点都能当 Transformer 的 query（和 DETR 的 Object Query 一个套路）。

### 3.3 Planner — 矢量空间的显式规划（VAD 最亮眼的创新）

**这是 VAD 最亮眼的创新：在矢量空间中做显式碰撞检测和规划优化。**

```python
# 传统方法 (UniAD): 用 NN 黑盒预测规划轨迹
# VAD: 用矢量信息做显式 optimization

def vad_planner(ego_state, agent_trajs, lane_graph, nav_cmd):
    # 1. 采样候选轨迹 (根据车道 + 导航)
    candidates = sample_trajectories(lane_graph, nav_cmd)
    # → K 条候选轨迹 (如 K=32)

    # 2. 对每条候选轨迹评分
    scores = []
    for traj in candidates:
        # 安全分: 与 agent 轨迹的最近距离
        safety = min_distance(traj, agent_trajs)
        # 舒适分: 加速度 / 曲率
        comfort = smoothness(traj)
        # 进度分: 向目标前进的距离
        progress = toward_goal(traj, nav_cmd)

        score = w1*safety + w2*comfort + w3*progress

    # 3. 选最高分的轨迹
    best_traj = candidates[argmax(scores)]
    return best_traj
```

**关键设计**: 候选轨迹采样 + 矢量化评分 → **可解释、可调试**。如果车跑偏了，可以检查是 safety 分太低还是 progress 分太低。

> [!question] 追问: 为什么不用 RL 直接输出规划？

因为 RL 在安全关键场景中不可解释。VAD 的显式优化方法：
- 每个评分项 (safety/comfort/progress) 可独立调参
- 可以人工注入安全约束 (min_distance < 1m → force 0 score)
- 出了问题可以回溯: 是采样不够密还是评分函数有问题

> [!note] "显式规划"vs"隐式规划"（务必理解）
> - UniAD：神经网络直接"预测"轨迹（黑盒）——你只能看到输出，不知道为什么选这条。
> - VAD：**先采样 32 条候选，再逐条打分（安全/舒适/进度），选最高分**（白盒）——每条轨迹为什么没被选，一目了然。
> 显式规划 = **把"决策"从"学出来的黑盒"变成"可审计的评分过程"**。这对量产安全验证是质变：出了事故，工程师能查出"是 safety 分没惩罚够，还是采样没覆盖那条路"。

## 四、训练细节

### 训练配置

| 项目 | 值 |
|------|-----|
| Backbone | ResNet-50 (ImageNet pretrain) |
| BEV Encoder | 简化版 BEVFormer (3 layers vs 6) |
| Epochs | 60 (nuScenes) |
| Batch Size | 4 (8 GPUs × 0.5 per GPU, gradient accumulation) |
| LR | 2×10⁻⁴, Cosine Annealing |
| 训练时间 | ~36h (8×A100) |

> [!note] 从配置读出的两个信息
> - **BEV Encoder 只用 3 层（BEVFormer 用 6 层）**：因为 VAD 不依赖稠密 BEV 特征的"精细度"，够提取车道/agent 就行——**表示变稀疏，特征提取也变轻**。
> - **0.5 per GPU + gradient accumulation**：即每 GPU batch=0.5（即 2 GPU 拼 1 个样本），说明显存压力大（多模态 + 时序），用梯度累积凑大 batch——[[模型基础知识补充]] 讲过的小 batch 技巧。

### 损失函数

```
L_total = L_det + L_map + L_motion + L_plan

L_det (agent检测):  Focal Loss + L1 (类似 DETR)
L_map (车道检测):   L1 for polyline points
L_motion (轨迹预测): L2 for agent trajectory points
L_plan (规划):      L2 imitation (vs human driver traj)
```

> [!note] 注意：VAD 的规划损失只有"模仿"（L2 vs 人类轨迹），没有 UniAD 的"安全/舒适"项——为什么？
> 因为 VAD 的安全性**不在损失里，而在 Planner 的评分函数里**（safety/comfort 是显式打分项）！
> **安全性从"学出来的"变成"写出来的"**——这是 UniAD（隐式）和 VAD（显式）在安全哲学上的根本区别：一个靠损失约束，一个靠规则评分。

## 五、面试官深度追问

### Q1: VAD 的矢量输出如果 agent 数量变化很大怎么办？

VAD 的 agent query 也是固定数量（如 300），类似 DETR/DETR3D 的设计。多余 query 输出 "no object" 类别。Agent 数量变化在 ±30 范围内 → 300 queries 有足够冗余。

### Q2: 矢量化丢失了哪些信息？有什么代价？（高频！）

丢失的信息：
1. **稠密空间信息**: 占据栅格中有 "路面" vs "人行道" 的精细信息 → 矢量只存车道线
2. **未知障碍物**: 如果有个 agent 检测漏了 → 占据栅格还能靠几何发现障碍 → 矢量没有
3. **Cost**: 矢量化的车道需要额外训练 Map Head → 增加了模型复杂度

这就是为什么最新的华为 ADS 3.0 同时输出 GOD (稠密占据) + 矢量检测 — **稠密做安全兜底，稀疏做高效规划**。

> [!warning] Q2 是面试杀手题，回答框架
> **先承认损失（诚实）→ 再给工业界的答案（互补）**。矢量化确实丢"稠密空间信息"和"未知障碍物兜底"，所以量产方案（华为 GOD）是**稠密（安全兜底）+ 稀疏（高效规划）并存**——不是二选一，是互补。能说出这个的候选人，说明理解"表示选择"不是非此即彼。

### Q3: 采样 32 条候选轨迹够吗？为什么不用 optimization-based planner？

采样-based 的优缺点：

优点: 简单、并行、可解释
缺点: 32 条可能不够 → 最优轨迹可能在采样空间之外

实际工程中，32 条配合 lane graph 引导覆盖了 >95% 的正常驾驶场景。对于极端场景（如紧急避让）→ 需要增加采样密度或切换到 optimization-based。

目前趋势 (2024): 采样 + optimization 混合 — 采样做粗搜索 → optimization 做精调。

### Q4: VAD 能处理无保护左转吗？（面试高频！）

VAD 可以，但依赖于 agent motion prediction 的质量。无保护左转需要：
1. 准确预测对向车辆的未来轨迹（Motion Head）
2. 候选轨迹 scoring 中高权重 safety → 只在安全时执行左转
3. 但**如果 agent motion 预测错误**（对向车突然加速），VAD 无法实时适应 → 需要闭环反馈

这是所有端到端模型的共同弱点 — 对罕见/对抗场景的泛化有限。

## 六、VAD 与 UniAD 的核心差异总结

| | UniAD | VAD |
|---|---|---|
| **设计哲学** | 感知特征服务规划 | 矢量表示服务规划 |
| **规划方式** | 隐式 (NN 黑盒) | **显式** (candidate scoring) |
| **可解释性** | 低 | **高** |
| **计算量** | 大 (dense throughout) | 小 (sparse after encoding) |
| **安全验证** | 难 | 易 (可审计 scoring) |
| **落地前景** | 研究 | **量产可行** |

**关键洞察**: VAD 证明了 "稀疏表示 + 显式规划" 不仅在效率上优于 UniAD，在精度和安全性上也有优势 — 这是 2023-2024 年端到端自动驾驶最关键的范式转换。

> [!note] 一条线串起来：UniAD → VAD → 华为 ADS
> - UniAD：证明"感知-规划一体化"可行（范式奠基）。
> - VAD：证明"稀疏表示 + 显式规划"更高效更安全（范式优化）。
> - 华为 ADS：把"稠密兜底 + 矢量高效 + 显式评分 + 规则兜底"全部工程化（范式量产）。
> **理解这条线，你就理解了端到端自动驾驶从论文到量产的全部演进逻辑。**

## 七、常见误区速查

> [!warning] 新手最常踩的坑
> 1. **以为矢量化是"压缩技术"**——不只是压缩！它是**表示范式的改变**：从"稠密网格表示世界"变成"稀疏矢量表示世界"，直接影响规划方式（显式 vs 隐式）。
> 2. **以为 VAD 的规划损失里有安全项**——没有！安全性在 Planner 的**评分函数**里（显式规则），不在损失里（隐式约束）。
> 3. **以为"稀疏 = 能力弱"**——VAD 用 R50 打赢 UniAD 的 R101，说明稀疏表示在规划任务上**更聚焦**，不是更弱。
> 4. **忽略矢量化丢信息的代价**——它确实丢了稠密空间信息和未知障碍物兜底，工业界用"稠密+稀疏并存"弥补（华为 GOD）。
> 5. **以为采样 32 条轨迹够用**——覆盖 95% 正常场景，极端场景需要采样+优化混合——"够用"和"完备"是两回事。

## ✅ 检验自己（自测题）

> [!question] Q1：说出"驾驶决策的最小信息集合"是什么，并解释为什么它们是稀疏的。
> 提示：4 类信息。

> [!success]- 参考答案
> ① 周围 agent 的位置和运动（矢量化轨迹）；② 车道拓扑（lane graph）；③ 交通灯状态（分类标签）；④ 自车状态（速度/加速度/朝向）。它们全部是稀疏的——agent 数量 O(10-100)、车道线数量 O(10-100)，而非 640K 体素。既然规划只需要稀疏信息，稠密表示就是浪费——这是 VAD 矢量化设计的理论基础。

> [!question] Q2：VAD 为什么比 UniAD 快 3 倍？只靠"表示变稀疏"吗？
> 提示：表示 → 计算 → 后处理。

> [!success]- 参考答案
> 不只是表示，是整个链路都变轻：① 表示稀疏（agent 轨迹/车道线 vs 稠密 BEV+占据），Planner 输入从 640K 格子降到 O(100) 矢量；② Backbone 更轻（R50 vs R101）、BEV Encoder 只用 3 层（vs 6 层）；③ 输出直接可消费（矢量轨迹直接给 Planner，不需要 heatmap 后处理）。三层叠加 = 3 倍加速，还更准。

> [!question] Q3："显式规划"和"隐式规划"的本质区别是什么？为什么显式更适合量产？
> 提示：可解释性、可调参、可审计。

> [!success]- 参考答案
> 隐式（UniAD）：神经网络直接预测轨迹，黑盒，无法解释"为什么选这条"。显式（VAD）：采样 K 条候选 + 逐条评分（安全/舒适/进度）+ 选最高分，白盒。显式适合量产因为：① 每个评分项可独立调参；② 可人工注入安全约束（如最小距离强制 0 分）；③ 出问题可回溯（是采样不够还是评分函数错）。可审计性是安全验证的前提。

> [!question] Q4：矢量化丢失了什么信息？工业界怎么弥补？（必考）
> 提示：稠密空间、未知障碍物。

> [!success]- 参考答案
> ① 稠密空间信息（路面 vs 人行道的精细语义，矢量只存车道线）；② 未知障碍物兜底（agent 漏检时，占据栅格还能靠几何发现，矢量不能）；③ 额外复杂度（Map Head）。工业界弥补：华为 ADS 3.0 同时输出 GOD（稠密占据，做安全兜底）+ 矢量检测（高效规划）——稠密与稀疏互补，不是二选一。

> [!question] Q5：VAD 的规划损失为什么没有"安全项"？它的安全性体现在哪？
> 提示：损失 vs 评分函数。

> [!success]- 参考答案
> VAD 的 L_plan 只有模仿项（L2 vs 人类轨迹），安全性不在损失里，而在 Planner 的显式评分函数里（safety 是打分项，可注入硬约束如 min_distance<1m 强制 0 分）。这是"安全性从学出来的变成写出来的"——和 UniAD 用损失约束安全形成根本对照：一个隐式，一个显式。

> ① 如果把权重改成 safety=0.9，结果变吗？② 如果对向车突然加速（预测错误），这套评分器能兜住吗？（不能——这正是 Q4 说的闭环反馈问题。）
