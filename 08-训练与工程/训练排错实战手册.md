## 〇、大白话总览

### 训练出问题 = 病人来看病

```
症状 1: Loss = NaN    → "发烧到 40 度"（数据/计算溢出）→ 第二节
症状 2: Loss 不下降   → "病情没好转"（LR/梯度/模型）→ 第三节
症状 3: Loss 震荡     → "病情反复"（batch/LR/多任务）→ 第四节
症状 4: 过拟合        → "复发了"（train 好 val 差）→ 第五节
症状 5: 多卡不一致    → "各科室说法不一"（同步问题）→ 第六节
```

> [!note] 最重要的总原则（先记住）
> **"先确认模型能过拟合小数据，再怀疑其他"**——在 100 个样本上关掉所有正则化，loss 应该能降到接近 0。**能过拟合 = 模型/数据没问题（调参问题）；不能过拟合 = 代码/数据 bug（先修 bug）。** 这一条能帮你省掉 80% 的瞎调参。

## 一、Loss 异常 — 系统性排查框架

### 1.1 排查决策树

```
Loss 异常
├── Loss = NaN → 跳转到 §2
├── Loss 不下降 → 跳转到 §3
├── Loss 震荡 → 跳转到 §4
├── Loss 下降但 val 不降 → 跳转到 §5
└── 多 GPU loss 不一致 → 跳转到 §6
```

### 1.2 总原则

> **先确认模型能过拟合小数据，再怀疑其他**。
> 在 100 个样本上关掉所有正则化 → loss 应该降到接近 0。如果不能 → 代码/数据 bug。如果能 → 调参问题。

> [!warning] 决策树的使用姿势
> **先判症状再动手**——不要"看到 loss 不对就调 LR"。按树走：NaN → §2，不降 → §3……**"对症下药"比"乱试药"快 10 倍**。这条决策树本身就是面试题的答案框架。

## 二、Loss = NaN

### 2.1 排查顺序

```
Step 1: 检查数据
  - 输入是否有 NaN/Inf? → print(torch.isnan(input).any())
  - 标签是否在合法范围? (bbox 坐标、类别 ID)
  - 归一化是否正确? (mean/std 除零?)

Step 2: 定位 NaN 产生点
  # 用 torch.autograd.detect_anomaly() 定位:
  with torch.autograd.detect_anomaly():
      loss = model(batch)
      loss.backward()  # 哪个 op 产生 NaN → 会报错

Step 3: 常见 NaN 源头
  - log(0) → 加 eps=1e-8
  - softmax 输入过大 → 检查是否做了合理的初始化
  - sqrt(负数) → 检查 loss 中是否有平方根
  - 除零 → IoU 计算的 denominator 加 eps
  - FP16 overflow → 改 BF16 或把那层改 FP32

Step 4: 梯度裁剪无效时
  - 梯度裁剪只解决传播中的梯度爆炸
  - 如果计算 loss 时就已经 NaN → clip 无用 → 回到 Step 3
```

> [!note] 排查顺序的逻辑（为什么先数据）
> **"NaN 最常来自数据，不是模型"**——输入带 NaN（读到损坏的图/标签越界）是最常见源头。**先查数据（免费）→ 再定位 op（detect_anomaly 自动找）→ 再改计算（加 eps）→ 最后怀疑精度**。从"最便宜"到"最贵"排查。

### 2.2 FP16 特有的 NaN 问题

```python
# FP16 动态范围: 6e-8 ~ 65504
# 常见溢出场景:

# 1. exp() 溢出 (Attention softmax 的 exp(QK^T/√d)):
# QK^T 可能 > 11 (exp(11) > 65504 → overflow)
# 解决: 用 FP32 做 softmax, 或缩小 attention scale

# 2. 大 batch 的 loss = sum of many terms:
# 16个样本的 loss 之和可能 > 65504
# 解决: loss = loss.mean() 而非 loss.sum()

# 3. 深度估计网络的 depth bin 概率:
# depth_dist = softmax(net(x))  # OK, softmax 输出 ≤ 1
# frustum_feats = feat * depth_dist  # OK
# 但 voxel pooling 的 sum 可能溢出 → 改 mean pooling
```

> [!warning] FP16 NaN 的三个"经典炸弹"（面试爱问）
> ① **exp 溢出**：softmax 的输入 > 11 就爆（[[Transformer架构详解]] 的 √d_k 缩放也防这个）；② **loss.sum()**：大 batch 求和超 65504（用 mean）；③ **voxel pooling sum**：累加溢出（改 mean）。**"FP16 NaN → 先想这三个"是面试标准话术。**

## 三、Loss 不下降

### 3.1 快速诊断清单

```
□ 打印 loss 的具体值: 是 10? 0.1? 0.001? → 判断尺度
□ 做小数据过拟合测试: 100 样本, 无 augment, 无正则化
□ 检查 LR: 太大(震荡)还是太小(不降)?
□ 检查梯度: 打印每层的 gradient L2 norm
□ 可视化: 看模型输出 vs ground truth
```

### 3.2 LR 诊断

```python
# LR Range Test (Leslie Smith):
def lr_range_test(model, dataloader, lr_start=1e-7, lr_end=10):
    lrs = []
    losses = []
    for batch in dataloader:
        lr = lr_start * (lr_end / lr_start) ** (len(lrs) / 100)
        for param_group in optimizer.param_groups:
            param_group['lr'] = lr
        loss = model(batch)
        loss.backward()
        optimizer.step()
        lrs.append(lr)
        losses.append(loss.item())
        if loss > 10 * min(losses):
            break  # 发散 → 停止

# 最佳 LR ≈ loss 下降最快的点的 LR / 10
# BEV 模型通常是 1e-4 ~ 5e-4 (AdamW)
```

> [!note] LR Range Test 的价值（面试谈资）
> 与其猜 LR，不如**扫一遍**：从 1e-7 指数增长到 10，画 loss-LR 曲线——**"loss 下降最快的点 /10"就是最佳 LR**。这是"用实验代替感觉"的典范（[[模型基础知识补充]] 的 LR 策略实战化）。

### 3.3 梯度诊断

```python
# 打印每层的梯度范数
total_norm = 0
for name, param in model.named_parameters():
    if param.grad is not None:
        param_norm = param.grad.data.norm(2)
        total_norm += param_norm.item() ** 2
        if param_norm > 10:  # 异常大
            print(f"⚠ {name}: grad_norm={param_norm:.2f}")
        elif param_norm < 1e-5:  # 消失
            print(f"⚠ {name}: grad_norm={param_norm:.6f} (vanishing)")

# 预期: 大部分层的 grad norm 在 0.01 - 1.0
# 如果第一层 < 1e-4 → vanishing gradient
# 如果最后一层 > 100 → exploding gradient
```

> [!note] 梯度诊断的两个"定位"意义
> - **vanishing（第一层梯度小）**：梯度传不到浅层 → 初始化/结构问题（[[计算机视觉基础]] 的 ResNet 残差就是为此）。
> - **exploding（最后层梯度大）**：深层梯度爆炸 → LR 太大 / 需要 clip。
> **"梯度范数"是训练的体温计**——打印一次梯度分布，问题定位快一半。

## 四、Loss 震荡

### 4.1 原因诊断

```
震荡模式分析:

高频小幅震荡 (step-to-step):
  原因: batch 太小, 每步的 gradient 噪声大
  诊断: 增大 batch_size 或 gradient accumulation
  验证: 看 moving average loss 是否平稳

周期性震荡 (每隔 N steps):
  原因: 数据排列有规律 (如按场景排序)
  诊断: shuffle dataset, 检查 DistributedSampler
  验证: 随机采样一个 batch → loss 应该变化大

缓慢大幅震荡 (epoch-level):
  原因: LR 太大 → optimizer 在最小值附近跳来跳去
  诊断: LR 缩小 10× 测试
  验证: 降低 LR 后震荡幅度变小

逐步发散:
  原因: 梯度爆炸的早期 → gradient norm 持续增大
  诊断: 检查 gradient clipping 是否生效
  验证: 打印 max(gradient_norm)
```

> [!warning] 读震荡模式的方法（面试核心）
> **"震荡的节奏"就是病因的线索**：step 级高频震荡 = batch 噪声；N-step 周期震荡 = 数据排列；epoch 级慢震荡 = LR 太大；逐步发散 = 梯度爆炸早期。**先看"震荡长什么样"再决定"改什么"**——面试答"loss 震荡怎么排查"就从这四个模式展开。

### 4.2 多任务震荡 — 最常见!

```python
# 检测 loss 在降，但规划 loss 在涨 → 多任务冲突
# 诊断:
for name, loss_component in losses.items():
    print(f"{name}: {loss_component.item():.4f}")

# 如果某个任务的 loss 是其他的 100× → 主导了梯度
# 解决:
# 1. Loss normalization: 将各 loss 归一化到相近量级
det_loss_normalized = det_loss / det_loss.detach()  # scale=1
seg_loss_normalized = seg_loss / seg_loss.detach()

# 2. 动态权重 (GradNorm):
# 监控每个任务的梯度范数变化率 → 动态调整权重
```

> [!note] 多任务震荡 = 智驾训练的"特产"
> 智驾模型几乎都是多任务（检测+分割+规划，[[UniAD详解]] 的分阶段训练就是为防这个）——**"一个任务在降、另一个在涨" = loss 尺度失衡**（检测 loss ~5 vs 规划 ~0.01，差 500 倍）。解法：归一化 / 动态权重 / 分阶段训练（[[AI-Infra详解]] 第七节的梯度管理）。

## 五、过拟合 — Loss 降但 Val 不降

```python
# 诊断步骤:
# 1. 确认是过拟合 (不是数据泄漏)
# train loss 持续下降 + val loss 先降后升 = 经典过拟合

# 2. 检查训练集和验证集的分布
# 如果 val set 的场景和 train 完全不同 → 不是过拟合, 是 domain gap

# 3. 对抗过拟合的手段 (按成本低→高):
a. 更强的数据增强: MixUp, CutMix, Mosaic (BEV 中要小心)
b. 增大 weight decay: 0.01 → 0.1
c. DropPath (对 ViT/Swin): 0.1 → 0.3
d. Label Smoothing: ε=0.1
e. Early Stopping (如果 val loss 连续 5 epochs 不降)
f. 减少模型容量 (更小的 backbone, 更少的 layers)
```

> [!warning] 先排除"假过拟合"（面试加分点）
> **train 降 + val 不降 ≠ 一定是过拟合**——先确认 val 分布和 train 是否一致：**如果 val 场景完全不同 → 是 domain gap（[[领域迁移与数据闭环]]），加正则化没用，要补数据**。**"先分诊（过拟合 vs domain gap），再用药"**——这是有经验工程师和无经验的差别。

## 六、多 GPU 训练问题

### 6.1 各 GPU loss 不一致

```python
# 问题: GPU0 loss=2.3, GPU1 loss=1.8, GPU2 loss=4.1

# 原因 1: 数据分配不均
# DistributedSampler 确保不重复, 但可能 GPU0 分到了更多 hard samples
# 验证: 检查每个 GPU 的 batch 中样本难度分布

# 原因 2: BN 不同步 (最常见!)
# 每个 GPU 的 BN 用自己 batch 的 stats → 小 batch 时不稳定
# 解决: 换成 SyncBatchNorm
model = torch.nn.SyncBatchNorm.convert_sync_batchnorm(model)

# 原因 3: 随机种子不同
# 确保每个 rank 使用相同的随机种子
torch.manual_seed(42 + rank)  # 错! ← 不同 rank 不同 seed
torch.manual_seed(42)         # 对! (DistributedSampler 处理数据差异)
```

> [!warning] 多卡不一致的三大元凶（面试背这三点）
> ① **BN 不同步**（最常见）——每卡 BN 用自己的 stats，小 batch 不稳定 → SyncBatchNorm；② **数据分配**——不同卡分到不同难度的样本（正常现象，看平均）；③ **种子**——`42+rank` 是错的！所有卡同一种子（DistributedSampler 负责数据差异）。

### 6.2 DDP 训练 hang 住不报错

```
常见原因:
1. 某个 GPU 的 batch 数据加载失败 → 其他 GPU 在 barrier() 无限等待
   → 加 try/except + dist.barrier() timeout

2. 不同 GPU 的模型结构不一致 (某 GPU 多了一层 dropout)
   → all-reduce 时参数数量不匹配 → hang
   → 验证: dist.all_reduce 前 assert 所有 rank 的 tensor 尺寸相同

3. NCCL 通信超时 (网络问题)
   → NCCL_DEBUG=INFO NCCL_TIMEOUT=1800 增加超时
```

> [!note] DDP hang 的本质：**"大家都在等最慢的那个"**
> DDP 的 barrier 同步 = 所有卡必须一起前进——**任何一张卡卡住，全部 hang**。所以：数据加载失败（加超时）、模型不一致（assert 尺寸）、NCCL 超时（加 timeout）——**"给等待加超时"是防 hang 的第一手段**。

## 七、面试官追问

### Q1: 训练一半突然 loss 暴涨到 NaN，你怎么快速恢复？

1. **立即停止** — 不要继续训，已经 NaN 的梯度会污染优化器状态
2. **回滚**: 从最近的 checkpoint (loss 正常时) 恢复
3. **降低 LR 10×** — 可能是 LR 太大导致的逐步发散
4. **开 FP32 重训 100 steps** — 确认不是 FP16 溢出
5. **增加 gradient clipping** (max_norm=1.0 而非 5.0)
6. **检查该 batch 的数据** — 保存下来可视化 → 可能有一张全黑/全白图
7. 如果以上都不行 → 可能是代码 bug → 回到 §2 的排查流程

> [!note] Q1 的答题逻辑：**"先止损，再定位"**
> 面试官想听的不是"我知道原因"，是"**你知道怎么快速恢复**"——① 停（止损）② 回滚（保住成果）③ 降 LR/FP32（试最可能原因）④ 查数据/代码（深挖）。**"恢复优先于诊断"** 是工程思维。

### Q2: 你训好一个模型，第二天用同样的代码和数据训，结果差很多 (不能复现)，怎么查？

经典的非确定性来源排查:

```python
# 1. 随机种子
torch.manual_seed(42)
torch.cuda.manual_seed_all(42)
np.random.seed(42)
random.seed(42)
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False  # 确定性模式 (但会慢 10-20%)

# 2. 数据加载
# DataLoader 的 worker_init_fn 需要设定种子
def worker_init_fn(worker_id):
    np.random.seed(42 + worker_id)

# 3. 模型初始化
# 某些层的默认初始化是随机的 → 检查所有层的 init 是否确定

# 4. cuDNN 算法选择
# cuDNN 默认会选择最快的算法 (非确定性)
# torch.backends.cudnn.deterministic=True → 强制用确定性算法

# 5. FP16 的浮点运算顺序
# a + b + c ≠ c + b + a (FP16 下非结合律)
# 无法完全消除 → 预期 ±0.1% 的浮动是正常的

# 如果完全 deterministic 后还有 >0.5% 差异 → 真的 bug
```

> [!note] Q2 的答题逻辑：**"先兜底，再归因"**
> 复现性问题五连查：种子（模型）→ worker 种子（数据）→ 初始化 → cuDNN 算法 → FP16 精度。**预期：完全 deterministic 后仍有 ±0.1% 浮动是正常的（FP16 非结合律）**；**>0.5% 才是真 bug**。**"知道什么是正常浮动"是复现性面试的隐藏考点。**

## 八、常见误区速查

> [!warning] 排错时最常踩的坑
> 1. **不看症状就调参**——"loss 不对就降 LR"是新手病；先走决策树判症状（NaN/不降/震荡/过拟合/多卡）。
> 2. **跳过小数据过拟合测试**——这是排错第一招（先证明模型能学），跳过它直接调参 = 瞎调。
> 3. **NaN 先怀疑模型**——NaN 最常来自数据（输入 NaN/标签越界），先查数据（免费）再动模型。
> 4. **混淆过拟合和 domain gap**——val 场景不同是 domain gap（补数据），不是过拟合（加正则）——先分诊。
> 5. **忽视"震荡节奏"**——震荡的模式（step 级/周期/epoch 级/发散）就是病因，看节奏再动手。
> 6. **多卡问题只怀疑模型**——BN 不同步/数据分配/种子是多卡不一致的三大元凶，SyncBatchNorm 先试。

## ✅ 检验自己（自测题）

> [!question] Q1：训练排错的第一步总原则是什么？为什么？
> 提示：小数据过拟合。

> [!success]- 参考答案
> "先确认模型能过拟合小数据，再怀疑其他"——在 100 个样本上关掉所有正则化，loss 应能降到接近 0。能过拟合 = 模型/数据没问题（调参问题）；不能过拟合 = 代码/数据 bug（先修 bug）。这一步把"模型坏了"和"参数没调好"分开，避免在坏模型上瞎调参（省 80% 时间）。

> [!question] Q2：Loss = NaN 的排查顺序是什么？
> 提示：数据→op→计算→精度。

> [!success]- 参考答案
> ① 先查数据（输入 NaN/标签越界/归一化除零）——NaN 最常来自数据；② 用 torch.autograd.detect_anomaly() 定位 NaN 产生的 op；③ 改计算（log(0) 加 eps、除零加 eps、softmax 输入过大）；④ 查精度（FP16 溢出：exp>11、loss.sum、voxel sum）。顺序逻辑：从最便宜（查数据）到最贵（改精度）。

> [!question] Q3：Loss 震荡的四种模式分别对应什么病因？
> 提示：节奏即病因。

> [!success]- 参考答案
> ① step 级高频小幅震荡 = batch 太小（梯度噪声大）→ 增大 batch/梯度累积；② 周期性震荡（每 N steps）= 数据排列有规律 → shuffle；③ epoch 级缓慢大幅震荡 = LR 太大（在最小值附近跳）→ 降 LR 10×；④ 逐步发散 = 梯度爆炸早期 → 检查 gradient clipping。多任务场景还要查"loss 尺度失衡"（检测 vs 规划差 500 倍）。

> [!question] Q4：train loss 降、val 不降，一定是过拟合吗？
> 提示：domain gap。

> [!success]- 参考答案
> 不一定。先分诊：① 如果 train 降 + val 先降后升 = 经典过拟合 → 加正则/增强/早停；② 如果 val 场景和 train 完全不同 = domain gap（[[领域迁移与数据闭环]]）→ 加正则没用，要补数据/域适应。**"先分诊（过拟合 vs domain gap），再用药"**——分错诊会白费力气。

> [!question] Q5：多卡训练各 GPU loss 不一致，三大元凶是什么？
> 提示：BN/数据/种子。

> [!success]- 参考答案
> ① BN 不同步（最常见）——每卡 BN 用自己 batch 的 stats，小 batch 不稳定 → SyncBatchNorm；② 数据分配不均——不同卡分到不同难度样本（正常，看平均）；③ 随机种子——`42+rank` 是错的，所有卡应同一种子（DistributedSampler 负责数据差异）。另外 DDP hang 的本质是"等最慢的卡"，要加超时/assert。

## 🛠 动手练习

### 练习 1：做一个"排错沙盒"（60-90 分钟）

故意制造 5 种训练 bug，用本篇工具排查：
1. 输入数据加 NaN（模拟损坏数据）→ 用 `torch.isnan(input).any()` 发现。
2. loss 用 sum 不用 mean（大 batch 溢出）→ 观察 FP16 下 NaN。
3. LR 设 0.1（过大）→ 观察 loss 发散，用 LR Range Test 找最佳 LR。
4. 不 shuffle 数据 → 观察周期震荡。
5. 多任务 loss 不归一化 → 观察"一个降一个涨"。

> [!tip] 这是"真训练过"和"跑过代码"的分水岭
> 亲手制造 + 亲手排查 5 种 bug，面试"loss 震荡怎么排查"就是送分题。每个 bug 用「症状 → 工具 → 根因 → 修复」四步记录，存进 [[2026-08-20]]。

### 练习 2：写"loss 震荡排查"面试答法（30 分钟）

用"先结论→展开→举例"写一段 250 字回答"训练 loss 震荡，你怎么排查？"：
1. 结论：先看震荡节奏（step/周期/epoch/发散）。
2. 展开：四种模式对应四种病因 + 多任务场景查 loss 尺度。
3. 举例：你（或练习 1 中）实际遇到的案例。

> [!tip] 完成标准
> 能说出"节奏即病因" + 至少 3 种模式的解法 + 一个真实案例（练习 1 的 bug 就是案例）。对照 [[模型基础知识补充]] 的 loss 曲线分析。

### 练习 3：给"复现性"写检查清单（可选，30 分钟）

基于 Q2 的五连查，写一份"训练前复现性检查清单"（seed/worker/init/cuDNN/FP16 预期浮动），贴在 [[本地训练方案]] 的环境搭建章节或你自己的训练脚本模板里。

> [!tip] 清单化 = 工程化
