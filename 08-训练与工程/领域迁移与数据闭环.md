## 〇、大白话总览

### "训练集 ≠ 真实世界"（一句话核心）

```
训练集: nuScenes（波士顿+新加坡、晴天为主、固定车型）
真实世界: 深圳/北京（早晚高峰、电动车加塞、夜间 30%）
→ 分布不一样 → 模型"水土不服"
```

> [!note] 打个比方
> 模型像"在波士顿学的驾照"——考试（val）全过，到了北京开车（上车）就懵：标志牌不一样、车流密度 3 倍、还有人逆行。**"考试环境和真实环境不同"就是 Domain Gap**——**"会考试 ≠ 会开车"是量产面试的第一课**（和 [[端到端自动驾驶概览]] 的"开环≠闭环"是同一个道理的两个侧面）。

### 两个概念的关系

```
Domain Gap:  模型在"新环境"为什么变差（静态问题）
数据闭环:    怎么通过"采集-标注-训练-上线"让它持续变好（动态解法）
→ 先诊断 Gap（量化），再用闭环修（迭代）
```

## 一、领域迁移 — 为什么 val 高 ≠ 上车好？

### 1.1 数据分布差异的具体来源

| 差异维度 | nuScenes (训练) | 真实路测 | 影响 |
|----------|---------------|---------|------|
| **地理** | Boston + Singapore | 深圳/北京/上海 | 道路结构、标志牌风格不同 |
| **天气** | 晴天为主 (80%+) | 雨/雾/雪/沙尘 | 相机画质退化，LiDAR 噪点增多 |
| **时段** | 白天为主 | 夜间 (30%) | 低光照 → 图像噪声大，物体特征弱 |
| **传感器** | 固定车型的固定传感器 | 不同车型、安装位置 | 相机内参/外参不同 |
| **场景密度** | 中等交通 | 中国早晚高峰 (3×密度) | 密集检测挑战 |
| **行为分布** | 美国/新加坡驾驶习惯 | 中国特色 (加塞/逆行/电动车) | Agent 行为预测失败 |
| **长尾场景** | 采样不足 | 真实频率更高 | Corner case 泛化差 |

### 1.2 量化 Domain Gap

```python
# 方法 1: 输入分布对比
# 计算训练集和路测数据的 image statistics
def compute_domain_gap(train_data, test_data):
    # Per-channel mean/std
    train_mean = train_data.mean(dim=(0,2,3))  # [C]
    test_mean = test_data.mean(dim=(0,2,3))
    
    # KL Divergence (假设高斯分布)
    kl_div = 0.5 * sum(
        (test_std / train_std)**2 + 
        ((train_mean - test_mean)**2) / train_std**2 - 1 +
        2 * log(train_std / test_std)
    )
    return kl_div

# 方法 2: 特征空间分析
# 用预训练 backbone 提取特征 → t-SNE 可视化
# 看训练/测试数据的特征 cluster 是否分离
from sklearn.manifold import TSNE
train_feats = backbone(train_imgs).flatten(1).numpy()
test_feats = backbone(test_imgs).flatten(1).numpy()
combined = TSNE(n_components=2).fit_transform(
    np.concatenate([train_feats, test_feats])
)
# 如果两个 cluster 明显分离 → Domain Gap 大 → 模型必然退化

# 方法 3: 类别分布对比 (Class Distribution Shift)
# 训练集: car 60%, pedestrian 15%, truck 10%...
# 北京实测: car 45%, pedestrian 25%, truck 5%, bicycle 20% (电动车!)
# → Class imbalance 导致少数类精度崩溃
```

### 1.3 Domain Gap 的典型修复方案

| 方案 | 成本 | 效果 | 何时用 |
|------|:--:|:--:|------|
| **收集+标注新域数据** | 高 | 最好 | 大版本迭代 |
| **Domain Adaptation (UDA)** | 中 | 中 | 无标注预算 |
| **Test-Time Adaptation** | 低 | 中低 | 在线调整 BN stats |
| **数据增强模拟新域** | 低 | 中 | 快速补救 |
| **LoRA 微调** | 中 | 好 | 小批新域标注数据 |

```python
# Test-Time Adaptation (最简单有效):
# 推理时用测试数据的 stats 更新 BN running mean/var
def adapt_bn_stats(model, test_batch):
    model.train()  # 开启 BN 更新
    with torch.no_grad():
        # 只用 BN 层更新，参数不变
        for module in model.modules():
            if isinstance(module, nn.BatchNorm2d):
                module.track_running_stats = True  # 更新 running stats
        _ = model(test_batch)
    model.eval()

# 效果: 典型场景 NDS +1-2 点提升 (几乎零成本)
```

## 二、数据闭环 — 从 Bad Case 到模型迭代

### 2.1 五步闭环 Pipeline

```
┌─────────────────────────────────────────────────────────┐
│                    数据闭环 (Data Flywheel)              │
│                                                          │
│  ① 触发采集      ② 数据回传      ③ 自动标注             │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐            │
│  │影子模式   │   │4G/5G/WiFi│   │大模型预标注│            │
│  │接管/碰撞   │ → │差分回传   │ → │人工修正    │            │
│  │不确定性高  │   │存储筛选   │   │质量检查    │            │
│  └──────────┘   └──────────┘   └──────────┘            │
│       ↑                              ↓                  │
│  ┌──────────┐                   ┌──────────┐            │
│  │OTA 部署   │ ←─────────────── │ 模型训练   │            │
│  │灰度发布   │                   │增量/全量  │            │
│  │AB Test   │                   │回归测试   │            │
│  └──────────┘   ← ⑤ 上线      └──────────┘  ← ④ 训练  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 触发采集 — 影子模式 (Shadow Mode)

```
影子模式: 模型在后台推理但不控制车辆，对比人类驾驶员 → 发现模型不足

触发条件 (怎么决定采集什么数据):
┌──────────────────────────────────────────────────────┐
│ 触发类型            │ 具体条件                        │
├─────────────────────┼─────────────────────────────────┤
│ 接管 (Disengagement) │ 人类驾驶员接管 → 必定触发       │
│ 碰撞风险             │ TTC < 2s → 紧急场景             │
│ 预测置信度低         │ detection confidence < 0.3     │
│ 不确定性高           │ 多模态预测的 entropy > 阈值     │
│ 场景稀缺             │ 夜间/雨雾/施工区 → 主动采集     │
│ 模型分歧             │ 旧模型 vs 新模型预测不一致      │
│ 规则触发             │ 地理围栏 (进入新城市)           │
└──────────────────────────────────────────────────────┘

# 关键: 不是采集所有数据! 要筛选"信息量大"的数据
# 指标: 每 MB 回传数据的模型改进量 (ROI of data)
```

### 2.3 数据回传 — 成本优化

```
问题: 单车日产 ~1TB 数据，1000 辆车 = 1PB/天 → 不可能全传

策略:
1. 差分压缩: 只传关键帧 (触发时刻前后 10s) → 减少 100×
2. 边缘筛选: 在车端用轻量模型判断"这个场景有价值吗" → 只传高分场景
3. 语义压缩: 不上传 raw 图像 → 传中间特征 + 元数据 (3MB/scene vs 500MB raw)
4. 分级回传:
   - P0 (接管/碰撞): 实时上传 (4G/5G)
   - P1 (低置信度): WiFi 上传 (回停车场后)
   - P2 (场景多样性): 抽检上传 (随机 1%)
5. 存储筛选: 上传后云端自动去重 → 相同场景只保留 1 份

实际成本: 
  raw upload: 1000 cars × 1TB/day = \$30M/month (云存储+带宽)
  optimized: 1000 cars × 3GB/day = \$90K/month → 300× 节省
```

### 2.4 自动标注 — 降低人工成本

```python
# 标注策略金字塔 (从便宜到贵):
# L1: 大模型预标注 (GPT-4V/Qwen-VL, $0.01/image)
# L2: 专用自动标注模型 (LiDAR→3D box projection, $0.001/box)
# L3: 多帧一致性自动标注 (track propagation, 零成本)
# L4: 人工审核 L1-L3 结果 ($0.5/box)
# L5: 纯人工标注 ($2-5/box, 仅用于极端 corner case)

# 实际流程:
# 1. 用大模型自动标注 10000 帧 → 置信度 > 0.9 的直接入库
# 2. 置信度 0.5-0.9 → 人工审核 (快速, 每人天 2000 帧)
# 3. 置信度 < 0.5 → 纯人工标注 (每人天 200 帧)
# 总成本: 10K 帧 × $0.05/帧 = $500 (vs 纯人工 $20000)
```

## 三、实战 — 给你 100 小时路测数据，只给 10% 标注预算

面试官丢出这个问题，考察的是**数据策略**而非模型能力。

**回答框架**:

```
1. 筛选 (Filtering) — 把 100h 压缩到 20h:
   - 去重: 连续相同场景只保留 1 帧/秒
   - 场景均衡: 高/快速路/城区/泊车 均匀采样
   - 难度过滤: 用旧模型跑一遍 → 选 loss 最高的 20% 帧

2. 优先级排序 — 20h → 按价值排序:
   Tier 1 (30% 预算, 60% 价值): 接管/碰撞帧 + 旧模型最差的场景
   Tier 2 (40% 预算, 25% 价值): 新场景类型 (旧训练集没见过的)
   Tier 3 (30% 预算, 15% 价值): 随机采样 (保证多样性)

3. 标注策略:
   - 对筛选后的 10h 数据:
     a. 自动标注模型预标注 (低成本)
     b. 人工审核 pre-label (中成本) — 占 70% 预算
     c. 纯人工标注 corner case (高成本) — 占 30% 预算

4. 闭环验证:
   - 用新旧数据混合训练 → 在保留的 2h hold-out set 上评估
   - 对比: 随机采样 10h vs 策略采样 10h → 策略采样的 NDS 提升预期 2-3×
```

## 四、面试官追问

### Q: 影子模式下，你怎么避免误触发？（比如晴天太阳直射导致置信度低）

**回答**: 多条件组合触发:
1. 不是单帧低置信度触发，而是连续 N 帧 + 空间一致性校验
2. 对比同场景其他传感器的置信度 (Camera 低 ≠ LiDAR 低)
3. 引入场景分类器: 如果检测到"太阳直射/雨天/镜面反射" → 标注为"环境原因"不触发采集
4. 统计频率: 某路段频繁触发 → 可能是该路段确实有问题 → 人工核实

### Q: 你标注的数据混入训练后，老场景精度反而降了怎么办？

**回答**: 这是灾难性遗忘的典型案例:
1. **原因诊断**: 新数据的类别/场景分布和旧数据差异大 → 模型偏向新数据
2. **验证**: 在旧测试集上跑一遍 → 确认精度退化
3. **修复**:
   - 混合训练: 旧数据 70% + 新数据 30% (经验比例)
   - EWC (Elastic Weight Consolidation): 对重要参数施加正则化
   - 数据回放 Buffer: 从旧数据中随机采样 10% 混入训练
   - 如果退化严重 → 冻结 Backbone + 只微调 Head (LoRA)

### Q: 如果你发现模型在某个特定路口频繁接管，你怎么处理？

这考察的是 **targeted data collection + root cause analysis**:

1. **数据回放**: 调取该路口所有 pass 的视频 → 回放分析
2. **分类问题**: 是检测漏了？跟踪断了？预测错了？规划不合理？
3. **针对性采集**: 专门派车在该路口不同时段/天气采集 → 构建 mini dataset
4. **快速修复**:
   - 如果是检测漏 → 标注该路口数据 → 针对性微调 detection head
   - 如果是规划问题 → 可能是地图/导航信号不好 → 加规则兜底
5. **验证**: 在该路口的 hold-out 数据上验证 → 确认修复 + 回归测试

## 五、常见误区速查

> [!warning] 新手最常踩的坑
> 1. **把"上车效果差"当模型问题**——先查 Domain Gap（数据分布），再动模型；"数据不对，模型白调"。
> 2. **以为 val 高 = 能上线**——val 集和训练集同分布，测不出 Domain Gap；**必须用"路测分布"的评测集**。
> 3. **只量化不修复**——算出 KL 散度就完了？要落到修复方案（采集/迁移/微调）——"诊断完必须给药"。
> 4. **全量回传所有数据**——1TB/车/天全传 = 天价；**差分压缩 + 边缘筛选 + 分级回传**（P0 实时/P1 WiFi/P2 抽检）。
> 5. **新数据直接混入训练**——灾难性遗忘（老场景退化）；**混合训练（旧 70% + 新 30%）+ 回放 Buffer**。
> 6. **忽视误触发**——影子模式单帧低置信度就触发 = 大量误报；**多条件组合 + 场景分类器过滤环境原因**。

## 六、检验自己（自测题）

> [!question] Q1：为什么"val 高 ≠ 上车好"？Domain Gap 的来源有哪些？
> 提示：分布差异。

> [!success]- 参考答案
> val 集和训练集同分布，测不出"新环境"的退化；上车的真实环境（地理/天气/时段/传感器/密度/行为/长尾）和训练分布不同。七个来源：地理（城市道路差异）、天气（雨雾雪）、时段（夜间）、传感器（车型/安装）、场景密度（早晚高峰）、行为分布（加塞/逆行/电动车）、长尾（corner case 频率）。核心："考试环境 ≠ 真实环境"。

> [!question] Q2：Domain Gap 怎么量化？至少说两种方法。
> 提示：输入/特征/类别。

> [!success]- 参考答案
> ① 输入分布对比：计算训练/路测的 per-channel mean/std，KL 散度量化；② 特征空间分析：backbone 提特征 → t-SNE 可视化，两个 cluster 分离 = Gap 大；③ 类别分布对比：训练集 vs 实测的类别比例差异（如电动车占比突变）→ 少数类精度崩溃。诊断方法决定修复方向。

> [!question] Q3：五种 Domain Gap 修复方案怎么选？
> 提示：成本×效果。

> [!success]- 参考答案
> ① 收集+标注新域数据（成本高、效果最好，大版本迭代用）；② Domain Adaptation UDA（中成本中效果，无标注预算时）；③ Test-Time Adaptation（低成本中低效果，在线调 BN stats，典型 +1-2 NDS）；④ 数据增强模拟新域（低成本中效果，快速补救）；⑤ LoRA 微调（中成本好效果，小批新域标注数据时）。选型 = "预算 × 紧迫性 × 数据可得性"。

> [!question] Q4：数据回传怎么省钱？1000 辆车一天 1TB/车，怎么做到 300× 节省？
> 提示：差分/筛选/分级。

> [!success]- 参考答案
> ① 差分压缩：只传触发时刻前后 10s 关键帧（减 100×）；② 边缘筛选：车端轻量模型判断"有价值吗"只传高分场景；③ 语义压缩：传中间特征+元数据（3MB vs 500MB raw）；④ 分级回传：P0 接管/碰撞实时（4G/5G）、P1 低置信度 WiFi、P2 场景多样性抽检 1%；⑤ 云端去重。优化后 3GB/车/天 ≈ 90K 美元/月 vs 全传 30M 美元/月（300× 节省）。

> [!question] Q5：给你 100 小时路测数据、10% 标注预算，你怎么做？
> 提示：筛选→排序→分层标注。

> [!success]- 参考答案
> ① 筛选：100h 压缩到 20h（去重/场景均衡/难度过滤——旧模型 loss 最高 20%）；② 排序：20h 按价值分 Tier（接管/碰撞帧 30% 预算 60% 价值 → 新场景 40% → 随机 25%）；③ 标注：自动预标注 + 人工审核（70% 预算）+ 纯人工 corner case（30%）；④ 验证：新旧混合训练 → hold-out 评估，对比随机采样（策略采样预期 NDS 提升 2-3×）。核心："数据策略 = 筛选 × 排序 × 分层标注"。

## 七、动手练习

### 练习 1：量化你的 Domain Gap（60 分钟）

用两个数据集（如 KITTI 和 Cityscapes）或训练/实测数据：
1. 计算 per-channel mean/std，用 KL 散度量化差异。
2. backbone 提特征 → t-SNE 画图，看 cluster 分离。
3. 写 3 句结论：你的数据 Gap 大吗？主要差在哪？

> [!tip] 这是"诊断"实战
> 亲手量化一次 Domain Gap，你就知道"上车效果差"该怎么排查。**t-SNE 图 = 面试时能展示的"证据"**。

### 练习 2：设计"100 小时数据 10% 预算"方案（45 分钟）

按第四节实战案例，写一份完整方案：
1. 筛选规则（去重/均衡/难度）。
2. Tier 排序与预算分配。
3. 标注策略（自动/审核/人工各多少）。
4. 验证方案（hold-out + 对比随机）。

> [!tip] 这是量产数据面试的"标准答案练习"
> 能写清楚"筛选×排序×分层标注"，面试"数据策略"题就稳了。对照第四节答案检查差异。

### 练习 3：做一个"影子模式触发"设计（可选，30 分钟）

设计一套影子模式触发规则（参照 2.2）：
1. 列出 5 种触发条件。
2. 每种怎么防误触发（多条件组合/传感器交叉/场景分类器）。
3. 估算：100 辆车一天触发多少次？回传多少数据（参照 2.3 的成本）？

> [!tip] 这是 [[数据闭环总览]] 的深入设计
> "触发 + 防误触 + 成本"三件套 = 影子模式的完整设计。做完对照 [[OTA更新与持续部署]] 的上线流程。
