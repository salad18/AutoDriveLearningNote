## 〇、大白话总览

### 四个话题 = 四层"研究素养"

```
① 评测:    "模型好不好"——不能只看一个 NDS，要分级分场景
② 消融:    "方法有没有用"——去掉它性能掉没掉，才能归因
③ GT:      "真值从哪来"——稠密 GT（占据）是"造"出来的
④ 模态统一: "多个传感器怎么对齐"——时间/空间/特征三维对齐
```

> [!note] 打个比方
> 四个话题对应四种"考试"：
> - **评测** = 期末考（不能只考一科，要分科（场景）考）
> - **消融** = 归因分析（"这门课提分是因为老师还是因为教材？"——一次只换一个变量）
> - **GT** = 标准答案（占据的"标准答案"不是人写的，是机器"造"出来的）
> - **模态统一** = 多科老师对表（时间/空间对不上，答案就对不上）
> **"会调参"只懂第一个，"会做研究"四个都懂**——面试官用这四个话题筛"工程素养"。

### 四个话题的串联（面试主线）

```
训练好模型 → 怎么证明它好？（评测）→ 好在哪里/为什么好？（消融）
→ 靠什么学出来的？（GT）→ 多传感器怎么配合？（模态统一）
→ 最后：能上车吗？（评测的 L4 层：闭环/影子模式）
```

## 一、模型评测与回归 (Evaluation & Regression)

### 1.1 评测体系金字塔

```
┌────────────────────────────────────────────┐
│            L4: 端到端系统评测               │
│   闭环: 仿真/路测/安全指标 (碰撞率/接管率)  │
├────────────────────────────────────────────┤
│            L3: 场景级评测                   │
│   场景分类: 高速/城区/夜间/雨雾 → 分组指标   │
├────────────────────────────────────────────┤
│            L2: 任务级评测                   │
│   检测: mAP/NDS | 跟踪: MOTA | 规划: L2    │
├────────────────────────────────────────────┤
│            L1: 单元级评测                   │
│   单模块: Backbone 精度/延迟/显存           │
└────────────────────────────────────────────┘
```

**核心思想**: 只靠一个 NDS 数字评测模型是危险的 — 必须分级、分场景、分模块评测。

### 1.2 回归测试 (Regression Testing)

**定义**: 每次模型/代码变更后，跑完整评测集，确认**新改动没有破坏已有能力**。

```
变更后 → 跑回归测试:
  ├── 全量验证集评测 (如 nuScenes val, 几千帧) → 对比 NDS/mAP 是否回退
  ├── 历史 bad case 集评测 → 确认修复的场景没有复发
  ├── 场景切片评测 → 逐场景对比 (夜间/雨天/远距) → 定位回退发生在哪
  └── 延迟/显存回归 → 确认新改动没引入性能回退
```

**关键设计: 评测集怎么建？**

```python
# 评测集设计原则:
# 1. 静态集: 固定版本的标注 + 固定划分 → 保证可比性 (可回滚对比)
# 2. 分层采样: 按场景/天气/时段/距离分层 → 保证覆盖面
# 3. 困难集: 专门收集 bad case → 防回归的"哨兵"

eval_sets = {
    'standard':   nuScenes_val,        # 标准对比集
    'hard':       hard_cases_1000,     # 历史失败场景 (哨兵)
    'night':      night_only_500,      # 场景切片
    'rain':       rain_only_300,
    'far':        distance>50m_800,    # 远距切片
    'edge':       edge_cases_200,      # 极端 corner case
}

# 回归门槛 (Regression Gate):
# 变更合并条件:
# 1. standard NDS 不低于 baseline
# 2. hard 集不劣化 (哨兵必须守住)
# 3. 任一场景切片劣化 > 1 NDS → 人工审核
```

### 1.3 评测指标的选择

| 任务 | 指标 | 陷阱 |
|------|------|------|
| 3D 检测 | NDS, mAP | NDS 对速度/属性权重高 → 只刷 NDS 会忽略定位 |
| BEV 分割 | mIoU | 路面占 50%+ → 加权平均会掩盖小类问题 |
| 跟踪 | MOTA, IDS | 只看 MOTA 忽略 ID 切换 |
| 占据 | mIoU per class, RayIoU | 几何准确 vs 语义准确要分开看 |
| 规划 | L2 error, 碰撞率 | L2 低 ≠ 安全 (可能贴着障碍物走) |

> 面试追问: "你怎么评估一个感知模型能不能上车？"
> 回答框架: ① 全量回归 (NDS 不降) ② 场景切片 (无灾难性退化) ③ 闭环仿真 (碰撞率/接管率) ④ 影子模式 (线上数据对比) ⑤ 人工抽查 (可视化 bad case)

## 二、消融实验 (Ablation Study)

### 2.1 什么是消融实验

**定义**: 逐步移除/替换模型的某个组件，观察性能变化，以验证该组件的贡献。

```
核心问题: "你凭什么说你的方法有效？"
         → 因为去掉它, 性能就掉了 → 它有效。
```

### 2.2 消融实验的设计范式

```
设计原则:
1. 单一变量: 一次只改一个组件 → 否则无法归因
2. 固定基线: 所有变体共享相同训练配置 (数据/epoch/lr)
3. 双向验证: 加组件 (+X) 和 去组件 (-X) 都要做
4. 报告完整: 不仅报最终指标, 要报每个中间变体

典型消融矩阵 (以 BEVFormer 为例):

| 配置 | NDS | 结论 |
|------|-----|------|
| Full model | 56.9 | 基线 |
| - Temporal SA | 51.8 | 时序融合贡献 +5.1 |
| - Spatial CA | 31.2 | 空间交叉注意力是核心 (+25.7!) |
| - 多尺度特征 | 54.3 | 多尺度贡献 +2.6 |
| - FOV mask | 52.1 | FOV 过滤贡献 +4.8 |
| + 更强 Backbone | 62.8 | 上限提升 |

结论解读:
- 去掉某组件性能大跌 → 该组件是关键
- 去掉某组件性能不变 → 该组件冗余 (可以删!)
- 组件之间交叉消融 → 发现依赖关系
```

### 2.3 消融实验的进阶类型

```python
# 1. 组件消融: 换/删组件
# 例: Deformable Attention → 标准 Attention → 对比

# 2. 超参消融: 扫超参
# 例: K=2/4/8 个采样点 → 找最优 trade-off

# 3. 数据消融: 换数据/量
# 例: 训练数据 10%/30%/100% → 画 learning curve
# 例: 有深度监督 vs 无深度监督 → 验证监督信号价值

# 4. 训练策略消融: 换训练配置
# 例: 24 epochs vs 60 epochs vs CBGS vs 无 CBGS

# 5. 结构变体消融: 换结构部件
# 例: Backbone ResNet-50 vs Swin-T vs ConvNeXt-B
```

### 2.4 面试官追问

**Q: 消融实验里去掉一个组件性能不变，说明什么？**

三种可能:
1. **组件冗余**: 该组件确实没用 → 可以删除 (省计算)
2. **功能重叠**: 另一个组件已经覆盖了它的功能 → 不是"没贡献"，是"贡献被吸收"
3. **实验设计问题**: 可能 baseline 太弱/太强，掩盖了组件效果 → 需要在更强的 baseline 上重新验证

关键区分: 用"功能重叠"来解释 (展示理解深度)，而不是简单说"没用"。

**Q: 消融实验的成本太高 (每跑一次 24 epochs 要 28 小时)，怎么控制？**

1. **先小数据集验证**: 在 10% 数据上做粗粒度消融 → 方向对了再全量
2. **缩短 epoch**: 12 epochs 的消融趋势和 24 epochs 通常一致
3. **冻结 Backbone**: 只消融 Head/Neck 部分 → 大幅省时
4. **并行**: 多个消融实验同时跑 (8 GPU 跑 8 个变体)
5. **只报关键差异**: 不是每个变体都全量 → 选最重要的 3-5 个

## 三、GT 构造 (Ground Truth Construction)

### 3.1 3D 检测 GT

```
GT 来源: 3D box 标注
流程:
1. LiDAR 点云 → 人工在 3D 视图标注 BBox (类别+长宽高+朝向+速度)
2. 多传感器时间对齐 → 每个 camera 的 box 投影回 2D 作为辅助监督
3. 质量检查: 交叉标注一致性 (double-annotation agreement)

GT 细节 (nuScenes):
- 10 个类别: car, truck, bus, trailer, construction, pedestrian, motorcycle, bicycle, traffic_cone, barrier
- 每帧标注: 所有 visible objects + 部分遮挡 objects
- 速度标注: 利用连续帧 box 位移计算 (automatic)
- 属性标注: 灯的状态、车辆姿态 (automatic from track)
```

### 3.2 占据网络 GT (稠密 GT 的构造 — 重点!)

```python
# 占据 GT 不是人工标注的! 是从稀疏点云 "稠密化" 生成的:

# Occ3D 流程:
# 1. 稀疏 LiDAR 点云 → 每个 voxel 有/无点
# 2. 多帧累积: 连续帧点云对齐叠加 → 填补被遮挡区域
# 3. Box 填充: 用 3D box 标注 → box 内部的 voxel 标为 "occupied + 语义"
# 4. 路面扩展: 检测到的地面平面 → 下方 voxel 标为 "driveable"
# 5. 未观测区域: 标为 "unknown" (不参与 loss 计算!)

# 关键: unknown 区域的处理
def occupancy_loss(pred, gt, unknown_mask):
    # unknown_mask: 未观测的 voxel
    # 计算 loss 时 mask 掉 unknown → 模型不需要猜没看到的地方
    loss = CE(pred[~unknown_mask], gt[~unknown_mask])
    return loss

# 面试考点: 为什么占据 GT 要标 unknown?
# → 因为模型无法从输入推断未观测区域 → 强迫它学 unknown 会伤害训练
# → 这是稠密 GT 和稀疏 GT 的关键区别 (检测 GT 没有 unknown 概念)
```

### 3.3 深度 GT (BEVDepth)

```python
# 深度 GT 从 LiDAR 自动生成 (零人工标注):
# 1. LiDAR 点云投影到图像平面 → 得到稀疏深度图
lidar_depth = project_lidar_to_image(lidar_points, K, RT)
# [H, W] 稀疏 (~10% 像素有值)

# 2. 转换为 D=128 bin 的 one-hot distribution
depth_bin = (lidar_depth / 0.4).long()  # 每 0.4m 一个 bin
depth_onehot = one_hot(depth_bin, 128)

# 3. 只对有值的像素计算 loss (valid_mask)
loss = BCE(depth_pred, depth_onehot) * valid_mask
```

### 3.4 GT 质量对模型的影响

| GT 质量问题 | 对模型的影响 |
|-------------|-------------|
| 标注偏移 (0.2m) | 检测精度上限被压缩 |
| 类别错误 | 训练信号冲突 → 模型困惑 |
| 遮挡目标漏标 | 模型把漏标目标当 FP → 过度抑制 |
| 密集场景漏标 | 同上, 且影响周围目标 |
| 时序不一致 | 速度/轨迹 GT 错误 → 预测学歪 |

> 面试追问: "如果给你的训练集 GT 有 5% 的错误，你会怎么办？"
> 回答框架: ① 先量化: 抽样核查错误类型 ② 数据清洗: 置信度过滤 + 人工复核 ③ 损失侧: label smoothing / 降低 hard 样本权重 ④ 主动学习: 模型难学且 GT 不一致的样本优先复核

## 四、模态统一 (Modality Alignment)

### 4.1 模态统一是什么

**定义**: 让不同传感器 (Camera/LiDAR/Radar) 的数据在**时间**和**空间**上对齐到同一参考系，使融合后的特征具有一致性。

```
模态不统一的后果 (用 60km/h 车举例):
  时间不同步 50ms → 位置偏差 0.83m → 融合后出现 "重影"
  空间标定漂移 0.5° → 30m 处偏差 0.26m → 检测框偏斜
  特征域不一致 → 模型学到的融合权重失效
```

### 4.2 时间维度统一

| 方案 | 精度 | 成本 | 说明 |
|------|:---:|:---:|------|
| **硬件同步 (PTP/PPS)** | <1ms | 高 | 传感器需支持硬件时间戳 |
| **软件时间戳对齐** | ~10ms | 低 | ROS message filter |
| **IMU 运动补偿插值** | <5ms | 中 | 用 IMU 积分补偿帧间运动 |

```python
# 时间对齐的核心: 运动补偿
# Camera 曝光时刻 t_c, LiDAR 扫描时刻 t_l (t_l < t_c)
# 用 IMU 积分 t_l→t_c 的自车运动, 补偿 LiDAR 点云
def motion_compensate(lidar_pts, imu_integral):
    T = imu_integral  # [4,4] ego motion from t_l to t_c
    compensated = T @ lidar_pts_homo
    return compensated
# → 补偿后 LiDAR 和 Camera 描述同一时刻的场景 → 空间融合才有意义
```

### 4.3 空间维度统一

```
空间统一 = 外参标定 (Extrinsic Calibration):
  Camera-LiDAR: 求解 [R|t] 使 LiDAR 点投影到图像上与视觉边缘对齐
  Camera-Camera: 多相机之间的旋转平移
  LiDAR-Radar: 雷达点云到 LiDAR 坐标系

标定方法:
  离线标定: 标定板/特征点 → 高精度, 出厂前完成
  在线标定: 行驶中实时估计外参漂移 → 补偿热胀冷缩/振动

外参漂移检测:
  LiDAR 投影到图像的边缘对齐误差 > 阈值 → 触发在线标定
```

### 4.4 特征维度统一 (最容易被忽视!)

**时间/空间对齐只是第一步 — 特征域的"对齐"同样关键**:

```
问题: Camera 特征和 LiDAR 特征不在同一特征空间
  Camera: 语义丰富 (RGB 纹理), 无精确深度
  LiDAR: 几何精确 (XYZ), 无语义

融合时:
  1. 直接 concat → 特征分布不同 → 模型需要学习两者关系 (慢)
  2. 投影对齐: LiDAR 特征投影到图像 BEV → 逐位置对应
  3. 注意力对齐: Cross-Attention 让相机 Query 从 LiDAR 特征采样 (BEVFusion)

BEVFusion (MIT) 的做法:
  Camera → BEV 特征 (通过 depth 投影)
  LiDAR → BEV 特征 (voxel)
  两者在 BEV 空间 concat → 同一坐标系下的特征融合
  → 但特征分布仍不同 → 用 BEV Encoder 网络学习融合
```

### 4.5 面试官追问

**Q: 模态统一中最难的是什么？**

答: **时间同步的精度**。因为:
- 空间标定可以做得很准 (离线标定 0.01°)
- 但时间同步受限于传感器硬件 (Camera 曝光延迟、LiDAR 扫描模式)
- 高速场景下时间误差的放大效应最明显 (0.1s 误差 = 2.8m @ 100km/h)
- 且时间同步错误**无法通过后处理完全恢复** (运动是时变的)

**Q: Camera 30Hz + LiDAR 10Hz，怎么对齐？**

答: 三步:
1. 以 Camera 曝光时刻为基准 (感知决策以视觉为主)
2. LiDAR 扫描 → 用 IMU 插值到 Camera 时刻 (运动补偿)
3. 多帧 LiDAR 累积 (前 5 帧) → 补偿到同一时刻 → 增加点云密度

**Q: 为什么 BEV 是天然的多模态统一空间？**

答: BEV 空间的物理意义明确 (x,y 是真实世界坐标) → 所有传感器都能投影到同一坐标系 → 不需要语义对齐, 只需要几何对齐 (外参) → 这是 BEV 成为主流融合范式的根本原因。

## 五、常见误区速查

> [!warning] 新手最常踩的坑
> 1. **只用一个 NDS 评测**——"一个数字评价模型是危险的"；必须分级（单元/任务/场景/系统）+ 分场景 + 分模块。
> 2. **消融不设基线/多变量同改**——一次只改一个组件，所有变体共享训练配置，否则无法归因（"不是消融是玄学"）。
> 3. **把"去掉组件性能不变"直接当"没用"**——可能是功能重叠（贡献被吸收）或 baseline 问题；要先区分再下结论。
> 4. **忽略占据 GT 的 unknown**——模型无法推断未观测区域，强迫学 unknown 会伤害训练；**loss 要 mask 掉 unknown**。
> 5. **以为模态统一 = 空间标定**——时间同步精度更难（硬件限制 + 运动时变 + 无法后处理恢复）；特征域对齐也常被忽视。
> 6. **GT 质量不检查**——5% 的 GT 错误会压缩精度上限、让模型困惑；先量化再清洗（抽样核查/置信度过滤/主动学习复核）。

## 六、检验自己（自测题）

> [!question] Q1：评测体系金字塔有哪四层？为什么"只靠一个 NDS 危险"？
> 提示：分级分场景。

> [!success]- 参考答案
> L1 单元级（单模块精度/延迟/显存）→ L2 任务级（检测 mAP/NDS、跟踪 MOTA、规划 L2）→ L3 场景级（高速/城区/夜间/雨雾分组指标）→ L4 系统级（闭环仿真/路测碰撞率/接管率）。只靠一个 NDS 危险：① 不同场景表现差异大（夜间/雨天可能灾难性退化被平均掩盖）；② 单指标可被"刷"（只刷 NDS 忽略定位）；③ 任务级好 ≠ 系统级安全。必须"分级 × 分场景 × 分模块"。

> [!question] Q2：回归测试怎么设计？"回归门槛"是什么？
> 提示：静态集/分层/困难集。

> [!success]- 参考答案
> 评测集设计：① 静态集（固定标注+划分，可回滚对比）；② 分层采样（场景/天气/时段/距离覆盖）；③ 困难集（历史 bad case 当"哨兵"）。回归门槛：① standard NDS 不低于 baseline；② hard 集不劣化（哨兵必须守住）；③ 任一场景切片劣化 >1 NDS → 人工审核。核心："新改动不能破坏已有能力"（防 [[数据闭环总览]] 的回归风险）。

> [!question] Q3：消融实验的设计原则？"去掉组件性能不变"怎么解读？
> 提示：单变量/基线/双向。

> [!success]- 参考答案
> 原则：① 单一变量（一次只改一个）；② 固定基线（所有变体共享训练配置）；③ 双向验证（+X 和 -X 都做）；④ 报告完整（报每个中间变体）。"去掉组件性能不变"三种可能：组件冗余（真没用可删）/ 功能重叠（贡献被吸收，不是没贡献）/ 实验设计问题（baseline 太弱太强掩盖效果）。区分用"功能重叠"解释展示理解深度。

> [!question] Q4：占据 GT 为什么有 unknown？loss 怎么处理？
> 提示：未观测。

> [!success]- 参考答案
> 占据 GT 是从稀疏 LiDAR 稠密化生成的（多帧累积 + box 填充 + 路面扩展），未观测区域标 unknown——**因为模型无法从输入推断没看到的地方，强迫学 unknown 会伤害训练**（稠密 GT 和稀疏 GT 的关键区别：检测 GT 没有 unknown 概念）。loss 处理：`CE(pred[~unknown_mask], gt[~unknown_mask])`——mask 掉 unknown 再算。

> [!question] Q5：模态统一最难的是什么？为什么？
> 提示：时间同步。

> [!success]- 参考答案
> 最难的是**时间同步的精度**：① 空间标定可做很准（离线 0.01°），时间同步受限于传感器硬件（Camera 曝光延迟、LiDAR 扫描模式）；② 高速下时间误差放大明显（0.1s = 2.8m @ 100km/h）；③ 时间同步错误无法后处理完全恢复（运动是时变的）。另有特征域对齐（Camera 语义 vs LiDAR 几何不在同一特征空间）常被忽视——BEV 是天然统一空间（只需几何对齐）。

## 七、动手练习

### 练习 1：搭一套评测体系（60 分钟）

给你的模型（或 [[本地训练方案]] 的 YOLO）搭评测体系：
1. 建 4 个评测集：standard / hard（历史失败）/ night / far（分层切片）。
2. 定义回归门槛（NDS 或 mAP 不降 + hard 集不劣化）。
3. 跑一次"改动前 vs 改动后"的回归对比。

> [!tip] 这是"评测回归"的实战
> 亲手搭一套评测集 + 门槛，面试"怎么评估能不能上车"就有实数据（"我建了 4 个评测集，hard 集当哨兵"）。

### 练习 2：设计一个消融矩阵（45 分钟）

对你的模型设计消融实验：
1. 列出 3 个要验证的组件（如：时序、多尺度、FOV mask）。
2. 画消融矩阵表（Full / -组件1 / -组件2 / ...）。
3. 估算每个变体的训练成本，设计"先小数据粗消融，再全量确认"的省钱流程。

> [!tip] 这是"会做研究"的标志
> 能设计规范的消融矩阵 + 控制成本（10% 数据粗消融 + 并行 + 冻结 backbone），面试"凭什么说方法有效"就稳了。

### 练习 3：模态统一分析（可选，45 分钟）

用 [[多传感器融合基础]] 的知识分析你的传感器配置：
1. 列出你的传感器频率/延迟（参照 4.1 表）。
2. 算"时间不同步 50ms @ 你的车速"的位置偏差。
3. 设计对齐方案（硬件同步？IMU 补偿？）——写出三步。

> [!tip] 这是"模态统一"的定量分析
> 亲手算"时间误差 → 位置偏差"，你就理解为什么同步是生死线（[[多传感器融合基础]] 的 10ms≈28cm）。做完存进 [[2026-08-20]]。
