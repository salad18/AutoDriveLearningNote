## 〇、大白话总览

### OTA 是什么？——"远程给车升级"

```
OTA (Over-The-Air) = 通过网络远程更新车辆的软件/固件/模型
像手机系统升级，但风险完全不同:
  手机: 升级失败 → 重试 → 不影响安全
  汽车: 升级引入 bug → 车行为异常 → 安全隐患!
       升级中断电 → 系统不可用 → 车无法启动!
```

> [!note] 打个比方
> - 手机 OTA = "换手机主题"（错了再换回来）。
> - 汽车 OTA = "给飞行中的飞机换引擎"（必须零风险、可回滚、不影响飞行）。
> **"零风险、可回滚、不影响行车安全"是汽车 OTA 的三条铁律**——所有流程设计都围绕这三条。

### OTA 是数据闭环的"最后一公里"

```
数据闭环: 采集 → 挖掘 → 标注 → 训练 → 评测 → [OTA] → 新数据 → ...
                                                  ↑
                              本篇：怎么把新模型安全送到百万台车上
```

> [!note] 为什么 OTA 是闭环的"引擎"？
> **模型再好，发不出去 = 闭环断掉**。华为"5 天迭代"（[[数据闭环总览]]）能成立，前提是"5 天能安全发一次 OTA"——**OTA 速度 = 数据闭环速度**（[[华为ADS技术方案]] 的迭代节奏靠 OTA 支撑）。

## 一、OTA 概述

### OTA 类型

| 类型 | 更新内容 | 大小 | 风险 | 频率 |
|------|----------|:--:|:--:|:--:|
| **SOTA** (Software OTA) | 应用层软件、模型权重 | MB~GB | 低 | 周/月 |
| **FOTA** (Firmware OTA) | 底层固件、ECU、系统 | GB | 高 | 季/年 |
| **地图 OTA** | 高精地图/导航数据 | GB | 低 | 日/周 |
| **模型 OTA** | 神经网络模型权重 | MB~GB | 中 | 周/月 |

### 自动驾驶 OTA 的特殊性

```
手机 OTA:
  更新失败 → 再试一次 → 不影响安全

汽车 OTA:
  更新引入 bug → 车辆行为异常 → 安全隐患!
  更新过程断电 → 系统不可用 → 车辆无法启动!
```

**汽车 OTA 必须满足**：零风险、可回滚、不影响行车安全。

> [!warning] "模型 OTA"是智驾的核心（面试谈资）
> 智驾迭代主要是**模型 OTA**（权重更新，周/月频率）——这也是 [[模型训练与微调]] "持续学习"和 [[数据闭环总览]] "5 天迭代"的落地通道。**"模型 OTA 频率" = 智驾迭代能力的直接体现**（华为 5 天 vs 传统车企以月计）。

## 二、OTA 全流程

### 标准化 Pipeline

```
┌──────────────────────────────────────────────────────────────┐
│                     OTA 完整流程                              │
│                                                              │
│  Step 1       Step 2        Step 3        Step 4             │
│  模型产出  →  验证测试  →  灰度推送  →  全量推送            │
│                                                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐       │
│  │ 训练完成  │ │ 离线评测  │ │ Canary   │ │ 分批推送  │       │
│  │ 模型打包  │ │ 仿真评测  │ │ 部署     │ │ 1%→5%→   │       │
│  │ 签名加密  │ │ 影子模式  │ │ 监控     │ │ 25%→100% │       │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘       │
│                                                              │
│  Step 5: 全量监控 → 异常? → 自动回滚                        │
└──────────────────────────────────────────────────────────────┘
```

> [!note] 五步的逻辑：**"层层设卡，逐步放行"**
> 打包（安全）→ 验证（防线）→ Canary（小范围试）→ 渐进（扩大）→ 回滚（兜底）。**每一步都是"验证过了才进下一步"**——"发布会式上线"是笑话，"五步门禁式上线"才是量产。

### 各阶段详解

#### Step 1: 模型打包与安全

```
模型文件 + 配置文件 → 压缩 → 加密 → 数字签名
    ↓
OTA 包 = {
  model_checkpoint.pt,
  preprocessing.py,
  postprocessing.py,
  model_config.yaml,
  calibration.bin,
  metadata.json
}
→ 签名 → 上传 CDN → 等待分发
```

#### Step 2: 验证测试（上线前的最后防线）

| 测试层 | 内容 | 规模 |
|--------|------|:--:|
| **单元测试** | 单个函数/模块正确性 | 1000+ tests |
| **回归测试** | 新模型在历史数据上的表现 | 100K+ 样本 |
| **回放测试** | 用真实传感器数据回放，对比输出 | 1000+ clips |
| **仿真测试** | 百万级虚拟场景测试 | 1M+ scenarios |
| **影子模式** | 在实车上后台运行，不控车 | 100+ vehicles |
| **封闭场地测试** | 真实道路场景验证 | 100+ km |

**测试必须覆盖**：
- ✅ 常规场景 (直行、跟车、变道)
- ✅ 已知 corner case (之前出过问题的场景)
- ✅ 对抗性场景 (故意设计让模型出错)
- ✅ 传感器故障注入 (摄像头遮挡、LiDAR 脏污)

> [!warning] 五层验证的"纵深防御"（面试谈资）
> **单元（函数对）→ 回归（历史数据不退化）→ 回放（真实数据对比）→ 仿真（百万场景）→ 影子/场地（实车）**——每层捕获不同 bug 类型。**"回归测试"是核心**（防 [[数据闭环总览]] 的"回归风险"——corner case 变好、常见场景变差）。**"传感器故障注入"是智驾特色**（真实世界传感器会坏，[[多传感器融合与故障降级]] 的量产验证）。

#### Step 3: Canary 部署

```
选择 0.1%-1% 的车辆作为"金丝雀" (Canary)
     ↓
推送新版本 → 严格监控 → 对比 Canary 组 vs 对照组
     ↓
监控指标:
  ├── 安全事件率 (AEB 触发/千公里)
  ├── 接管率 (人工接管/千公里)
  ├── 系统错误率
  ├── 推理延迟
  ├── 规划轨迹平滑度
  └── 用户满意度 (舒适度评分)

指标通过 → 扩大推送范围
指标异常 → 立即冻结，排查问题
```

> [!note] Canary 的直觉（为什么叫"金丝雀"）
> 矿工带金丝雀下矿——**金丝雀对毒气敏感，先死先报警**。Canary 部署 = 选 0.1-1% 的车先升级，**"用少数车试错，保护大多数车"**。**对照组对比是灵魂**：不是看 Canary 组指标好不好，是看 **Canary 组 vs 未升级组**的差异（排除天气/节假日等干扰）。

#### Step 4: 渐进式分阶段推送

```
验证通过后，分阶段扩大:

Phase 1: 1% 车辆   → 观察 24h
Phase 2: 5% 车辆   → 观察 48h
Phase 3: 25% 车辆  → 观察 72h
Phase 4: 100% 全量  → 持续监控

每个阶段设置自动门禁:
  IF 安全指标恶化 > 阈值 → 自动暂停推送
  IF 用户投诉增加 > 阈值 → 触发人工审查
```

#### Step 5: 自动回滚机制

```
车端存储 A/B 两个版本:
  ├── 当前运行版本 (Active)
  └── 上一个版本 (Rollback)

回滚触发条件:
  ├── 云端下发"回滚"指令
  ├── 车端检测到连续异常 (3 次系统错误)
  ├── 新版本运行 N 小时后自动激活 (watchdog)
  └── 特定信号触发 (如 CAN 总线异常)

回滚时间: < 1 秒
```

> [!warning] 自动回滚 = "兜底的兜底"（面试核心）
> 再好的验证也挡不住"没见过的场景"——**自动回滚是最后防线**：A/B 双版本 + 触发条件（云端指令/连续异常/watchdog）+ **<1 秒回滚**。**"回滚快"比"不出错"更现实**（出错必然发生，关键是出错后多久能退回来）。**A/B 双版本 = 车端永远有"上一个可用版本"**。

## 三、模型优化与部署

### 车端推理优化

| 技术 | 做法 | 加速比 |
|------|------|:--:|
| **量化 (Quantization)** | FP32 → INT8 | 2-4× |
| **剪枝 (Pruning)** | 移除冗余连接 | 1.5-3× |
| **蒸馏 (Distillation)** | 大模型教小模型 | 2-5× |
| **算子融合** | 合并 Conv+BN+ReLU | 1.2-1.5× |
| **TensorRT 编译** | GPU 指令优化 | 2-3× |
| **NPU 适配** | 昇腾/Orin 专用优化 | 3-5× |

### 华为 MDC 部署流程

```
PyTorch 模型
    ↓
昇腾 CANN 工具链:
  ├── ATC (Ascend Tensor Compiler) → OM 模型
  ├── 量化校准 (INT8/FP16)
  └── 图优化 (算子融合)
    ↓
MDC 平台部署:
  ├── MDC 610: 200 TOPS, 昇腾 610
  ├── MDC 210: 48 TOPS, 昇腾 310
  └── 轻量推理引擎
```

> [!note] 车端优化 = [[模型部署与延迟优化]] 的 OTA 场景版
> 量化/剪枝/蒸馏/TensorRT/NPU 适配——**全是 [[模型部署与延迟优化]] 的速查表内容**，本篇是"部署到 OTA 包"的落地。**"训练→优化→打包→OTA"是一条流水线**（PyTorch → ONNX/OM → 车端引擎）。

### A/B 模型同时运行

```
车辆运行:
  主模型 (Production):     实际控车 ← 安全第一
  影子模型 (Shadow Mode):   后台运行，不控车
                              ↓
                      对比主模型输出 vs 影子模型输出
                              ↓
              影子模型更好 → 标记该场景 → 下次作为回归测试
              影子模型更差 → 记录差异 → 分析原因
```

> [!note] A/B 运行 = 影子模式的 OTA 版
> **主模型控车 + 影子模型后台跑**——① 影子模式（[[数据闭环总览]]）收集"新模型 vs 现役"差异；② 新模型先在影子模式"实习"再转正。**"影子→Canary→全量"是模型上车的三级台阶**（先不控车试，再小范围控车试，最后全量）。

## 四、增量更新技术

### 增量更新 vs 全量更新

| 对比 | 全量更新 | 增量更新 |
|------|----------|----------|
| **包大小** | 数 GB | 数 MB-数百 MB |
| **下载时间** | 数十分钟 | 数分钟 |
| **适用** | 大版本升级 | 模型权重微调 |

### 模型增量更新

```
技术方案 1: 差分更新 (Delta Update)
  旧模型 vs 新模型 → 逐层对比 → 只传输变化的层

技术方案 2: LoRA 增量
  基础模型冻结 → 只更新 LoRA 适配器 (几 MB)

技术方案 3: 分层更新
  backbone 不动 → 只更新 task head
```

> [!note] 增量更新 = [[模型训练与微调]] 的"传输侧"
> **LoRA 微调（训练侧，参数少）→ LoRA 增量 OTA（传输侧，包小）**——**"训练时少训参数，OTA 时少传数据"是同一条效率逻辑**。**"基础模型 + 小适配器"架构让 OTA 从 GB 级降到 MB 级**——这是 [[模型训练与微调]] LoRA 的量产价值闭环。

## 五、监控与运维

### 车端实时监控

```
车端 Telemetry → 云端 Dashboard:

实时监控:
  ├── 模型推理延迟 (P50, P95, P99)
  ├── 模型输出分布漂移 (Distribution Shift)
  ├── 安全事件 (AEB、ESA 触发次数)
  ├── 系统资源 (CPU/GPU/Memory 占用)
  └── 传感器健康状态 (LiDAR 脏污检测等)
```

### 分布漂移检测 (Distribution Shift Detection)

```
训练数据分布 vs 实际运行数据分布:

检测方法:
  1. 输入空间漂移: 图像的统计特征 (亮度/对比度直方图)
  2. 特征空间漂移: 模型中间层激活分布
  3. 输出空间漂移: 检测框数量/大小的分布变化

漂移告警 → 可能需要重新训练/微调
```

> [!warning] 漂移检测 = 模型退化的"提前预警"（面试谈资）
> **部署后模型会随环境漂移退化**（新城市/季节/车型）——监控"输入/特征/输出"三空间漂移（[[常见面试题-感知算法]] Q20 的 Data Drift）。**"漂移告警 → 触发重新采集训练"** = 数据闭环的"自检机制"（[[领域迁移与数据闭环]] 的在线版）。

## 六、安全与合规

### OTA 安全

| 层面 | 措施 |
|------|------|
| **传输安全** | TLS 加密, CDN HTTPS |
| **包完整性** | 数字签名 (SHA-256 + 私钥) |
| **车端验证** | 验签 → 解密 → 安全启动验证 |
| **防重放攻击** | 时间戳 + Nonce |
| **权限管理** | 分级权限 (厂商/4S 店/用户) |
| **日志审计** | 完整 OTA 操作日志 |

### 合规要求

- **UN R156**：软件更新法规 (欧盟)
- **GB/T 标准**：中国 OTA 升级标准
- **OTA 升级必须可暂停/可回滚**
- **安全相关更新必须在规定时间内完成**

> [!note] 合规 = OTA 的"准生证"
> **OTA 不是想发就发**——欧盟 UN R156、中国 GB/T 都要求"可暂停/可回滚"（和本篇的自动回滚呼应）。**"安全合规"决定了 OTA 流程的硬约束**（法规要求的东西必须做）。

## 七、关键指标

| 指标 | 含义 | 华为 ADS 3.0 数据 |
|------|------|:--:|
| **迭代周期** | 模型新版本发布频率 | 每 5 天 |
| **OTA 成功率** | 成功更新 / 尝试更新 | > 99.5% |
| **更新包大小** | 每次 OTA 下载量 | - |
| **回滚时间** | 检测到问题→回滚完成 | < 1 秒 |
| **Canary 周期** | 灰度测试时长 | 24-72h |
| **安全事件率** | AEB 触发 / 千公里 | 持续下降 |

> [!note] 两个最该盯的指标
> - **OTA 成功率（>99.5%）**：百万辆车一次失败 0.5% = 5000 台车出问题——**成功率是可靠性的直接体现**。
> - **回滚时间（<1 秒）**：出错后多久能退——**"退得快"比"不出错"更现实**（和 [[华为ADS技术方案]] 的"5 天迭代 + 高可用"呼应）。

## 八、常见误区速查

> [!warning] 新手最常踩的坑
> 1. **把汽车 OTA 当手机 OTA**——汽车 OTA 引入 bug = 安全隐患，必须"零风险、可回滚、不影响行车"（手机"重试就行"）。
> 2. **跳过 Canary 直接全量**——没有灰度试探就全量推送 = 让百万辆车一起冒险；Canary 是"少数车试错保护大多数"。
> 3. **忽视对照组**——Canary 只看"新版本指标好不好"不对，必须对比"Canary 组 vs 未升级组"（排除天气等干扰）。
> 4. **以为验证一次就够**——五层验证（单元/回归/回放/仿真/实车）各防一种 bug，少一层多一分风险。
> 5. **忽略漂移监控**——部署不是终点，模型会随环境漂移退化（新城市/季节），必须持续监控 + 触发重训。

> [!question] Q1：汽车 OTA 和手机 OTA 的本质区别？汽车 OTA 的三条铁律？
> 提示：安全。

> [!success]- 参考答案
> 手机 OTA 失败可重试、不影响安全；汽车 OTA 引入 bug = 车辆行为异常 = 安全隐患，更新中断电 = 车无法启动。三条铁律：**零风险、可回滚、不影响行车安全**。所有 OTA 流程设计（验证/Canary/渐进/回滚）都围绕这三条——"给飞行中的飞机换引擎"。

> [!question] Q2：画出 OTA 五步流程，并说明每步防什么？
> 提示：打包/验证/Canary/渐进/回滚。

> [!success]- 参考答案
> ① 模型打包+签名加密（防篡改/注入）；② 五层验证（单元/回归/回放/仿真/实车——防各类 bug，回归防"退化"）；③ Canary（0.1-1% 车试错，对比对照组——防"大规模踩坑"）；④ 渐进推送（1%→5%→25%→100%，每阶段门禁——防"一步全量"）；⑤ 自动回滚（A/B 双版本 + <1s 回滚——兜底"没见过的场景"）。五步 = "层层设卡，逐步放行"。

> [!question] Q3：Canary 部署为什么必须"对比对照组"？
> 提示：排除干扰。

> [!success]- 参考答案
> 只看 Canary 组指标好坏不够——指标变差可能是天气/节假日/路段等外部因素，不是新版本的问题。**对比 Canary 组 vs 未升级组**（同时同地跑）才能隔离"版本带来的差异"——这是灰度发布的统计核心（和 AB 测试同原理）。

> [!question] Q4：自动回滚的触发条件有哪些？为什么"回滚快"比"不出错"更现实？
> 提示：A/B 双版本。

> [!success]- 参考答案
> 触发条件：云端回滚指令 / 车端连续异常（3 次系统错误）/ watchdog（新版本运行 N 小时后激活）/ 特定信号（CAN 异常）。回滚 <1 秒（A/B 双版本：车端永远有上一个可用版本）。为什么"回滚快"更现实：**再充分的验证也挡不住"没见过的场景"，出错是必然的**——关键是出错后多久能退回来（"退得快"是量产安全的现实保障）。

> [!question] Q5：增量更新怎么把 OTA 包从 GB 降到 MB？和训练侧什么呼应？
> 提示：LoRA。

> [!success]- 参考答案
> 三种方案：① 差分更新（只传变化的层）；② **LoRA 增量**（基础模型冻结，只传几 MB 的 LoRA 适配器）；③ 分层更新（backbone 不动只传 head）。呼应：**训练时"少训参数"（LoRA 微调）→ OTA 时"少传数据"（LoRA 增量）**——"基础模型 + 小适配器"架构让 OTA 从 GB 级降到 MB 级，[[模型训练与微调]] LoRA 的量产价值闭环。

## 🛠 动手练习

### 练习 1：设计一个 Canary 方案（30 分钟）

假设你要给 100 万台车推送新模型：
1. Canary 选多少车？（0.5% = 5000 台，合理吗？）
2. 监控哪 5 个指标？（安全事件/接管/错误/延迟/舒适度）
3. 怎么定义"对照组"？（随机分 2 组还是按车型/城市分？为什么？）
4. Canary 观察多久？（24h？够吗？）

> [!tip] 算完自问
> ① Canary 太小（0.01%）样本不足看不出差异，太大（10%）风险大——0.1-1% 是经验区间；② 对照组要随机（避免车型/城市偏差）；③ 观察时长要覆盖"高峰/低峰"（24h 至少覆盖一个完整日周期）。

### 练习 2：写"模型怎么安全上线"面试答法（45 分钟）

用"先结论→展开→举例"写一段 300 字回答"模型怎么安全上线？"：
1. 结论：五层验证 + Canary 灰度 + 渐进推送 + 自动回滚。
2. 展开：每步防什么（验证防 bug、Canary 防大规模踩坑、回滚兜底）。
3. 举例：华为 5 天迭代 + 99.5% OTA 成功率 + <1s 回滚。

> [!tip] 完成标准
> 能画出五步流程图 + 说出"回滚快比不出错更现实"+"对照组对比"两个亮点——面试官一听就知道你懂量产。

### 练习 3：设计增量更新方案（可选，30 分钟）

假设你的智驾模型每周微调一次（LoRA），设计增量 OTA：
1. 基础模型多大？LoRA 适配器多大？（估算 MB）
2. 差分更新和 LoRA 增量选哪个？为什么？
3. 增量 OTA 的安全验证和全量有什么不同？

> [!tip] 这是 [[模型训练与微调]]（LoRA）+ [[模型部署与延迟优化]]（包大小）的综合应用
> "训练侧少训参数 → OTA 侧少传数据"是同一个架构决策的两面。写完存进 [[2026-08-20]]。
