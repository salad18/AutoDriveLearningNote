# OTA 更新与持续部署

> 把训练好的模型安全、高效、可靠地部署到百万台车上。

---

## 一、OTA 概述

### OTA 类型

| 类型 | 更新内容 | 大小 | 风险 | 频率 |
|------|----------|:--:|:--:|:--:|
| **SOTA** (Software OTA) | 应用层软件、模型权重 | MB~GB | 低 | 周/月 |
| **FOTA** (Firmware OTA) | 底层固件、ECU、系统 | GB | 高 | 季/年 |
| **地图 OTA** | 高精地图/导航数据 | GB | 低 | 日/周 |
| **模型 OTA** | 神经网络模型权重 | MB~GB | 中 | 周/月 |

### 自动驾驶 OTA 的特殊性

```
手机 OTA:
  更新失败 → 再试一次 → 不影响安全

汽车 OTA:
  更新引入 bug → 车辆行为异常 → 安全隐患!
  更新过程断电 → 系统不可用 → 车辆无法启动!
```

**汽车 OTA 必须满足**：零风险、可回滚、不影响行车安全。

## 二、OTA 全流程

### 标准化 Pipeline

```
┌──────────────────────────────────────────────────────────────┐
│                     OTA 完整流程                              │
│                                                              │
│  Step 1       Step 2        Step 3        Step 4             │
│  模型产出  →  验证测试  →  灰度推送  →  全量推送            │
│                                                              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐       │
│  │ 训练完成  │ │ 离线评测  │ │ Canary   │ │ 分批推送  │       │
│  │ 模型打包  │ │ 仿真评测  │ │ 部署     │ │ 1%→5%→   │       │
│  │ 签名加密  │ │ 影子模式  │ │ 监控     │ │ 25%→100% │       │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘       │
│                                                              │
│  Step 5: 全量监控 → 异常? → 自动回滚                        │
└──────────────────────────────────────────────────────────────┘
```

### 各阶段详解

#### Step 1: 模型打包与安全

```
模型文件 + 配置文件 → 压缩 → 加密 → 数字签名
    ↓
OTA 包 = {
  model_checkpoint.pt,
  preprocessing.py,
  postprocessing.py,
  model_config.yaml,
  calibration.bin,
  metadata.json
}
→ 签名 → 上传 CDN → 等待分发
```

#### Step 2: 验证测试（上线前的最后防线）

| 测试层 | 内容 | 规模 |
|--------|------|:--:|
| **单元测试** | 单个函数/模块正确性 | 1000+ tests |
| **回归测试** | 新模型在历史数据上的表现 | 100K+ 样本 |
| **回放测试** | 用真实传感器数据回放，对比输出 | 1000+ clips |
| **仿真测试** | 百万级虚拟场景测试 | 1M+ scenarios |
| **影子模式** | 在实车上后台运行，不控车 | 100+ vehicles |
| **封闭场地测试** | 真实道路场景验证 | 100+ km |

**测试必须覆盖**：
- ✅ 常规场景 (直行、跟车、变道)
- ✅ 已知 corner case (之前出过问题的场景)
- ✅ 对抗性场景 (故意设计让模型出错)
- ✅ 传感器故障注入 (摄像头遮挡、LiDAR 脏污)

#### Step 3: Canary 部署

```
选择 0.1%-1% 的车辆作为"金丝雀" (Canary)
     ↓
推送新版本 → 严格监控 → 对比 Canary 组 vs 对照组
     ↓
监控指标:
  ├── 安全事件率 (AEB 触发/千公里)
  ├── 接管率 (人工接管/千公里)
  ├── 系统错误率
  ├── 推理延迟
  ├── 规划轨迹平滑度
  └── 用户满意度 (舒适度评分)

指标通过 → 扩大推送范围
指标异常 → 立即冻结，排查问题
```

#### Step 4: 渐进式分阶段推送

```
验证通过后，分阶段扩大:

Phase 1: 1% 车辆   → 观察 24h
Phase 2: 5% 车辆   → 观察 48h
Phase 3: 25% 车辆  → 观察 72h
Phase 4: 100% 全量  → 持续监控

每个阶段设置自动门禁:
  IF 安全指标恶化 > 阈值 → 自动暂停推送
  IF 用户投诉增加 > 阈值 → 触发人工审查
```

#### Step 5: 自动回滚机制

```
车端存储 A/B 两个版本:
  ├── 当前运行版本 (Active)
  └── 上一个版本 (Rollback)

回滚触发条件:
  ├── 云端下发"回滚"指令
  ├── 车端检测到连续异常 (3 次系统错误)
  ├── 新版本运行 N 小时后自动激活 (watchdog)
  └── 特定信号触发 (如 CAN 总线异常)

回滚时间: < 1 秒
```

## 三、模型优化与部署

### 车端推理优化

| 技术 | 做法 | 加速比 |
|------|------|:--:|
| **量化 (Quantization)** | FP32 → INT8 | 2-4× |
| **剪枝 (Pruning)** | 移除冗余连接 | 1.5-3× |
| **蒸馏 (Distillation)** | 大模型教小模型 | 2-5× |
| **算子融合** | 合并 Conv+BN+ReLU | 1.2-1.5× |
| **TensorRT 编译** | GPU 指令优化 | 2-3× |
| **NPU 适配** | 昇腾/Orin 专用优化 | 3-5× |

### 华为 MDC 部署流程

```
PyTorch 模型
    ↓
昇腾 CANN 工具链:
  ├── ATC (Ascend Tensor Compiler) → OM 模型
  ├── 量化校准 (INT8/FP16)
  └── 图优化 (算子融合)
    ↓
MDC 平台部署:
  ├── MDC 610: 200 TOPS, 昇腾 610
  ├── MDC 210: 48 TOPS, 昇腾 310
  └── 轻量推理引擎
```

### A/B 模型同时运行

```
车辆运行:
  主模型 (Production):     实际控车 ← 安全第一
  影子模型 (Shadow Mode):   后台运行，不控车
                              ↓
                      对比主模型输出 vs 影子模型输出
                              ↓
              影子模型更好 → 标记该场景 → 下次作为回归测试
              影子模型更差 → 记录差异 → 分析原因
```

## 四、增量更新技术

### 增量更新 vs 全量更新

| 对比 | 全量更新 | 增量更新 |
|------|----------|----------|
| **包大小** | 数 GB | 数 MB-数百 MB |
| **下载时间** | 数十分钟 | 数分钟 |
| **适用** | 大版本升级 | 模型权重微调 |

### 模型增量更新

```
技术方案 1: 差分更新 (Delta Update)
  旧模型 vs 新模型 → 逐层对比 → 只传输变化的层

技术方案 2: LoRA 增量
  基础模型冻结 → 只更新 LoRA 适配器 (几 MB)

技术方案 3: 分层更新
  backbone 不动 → 只更新 task head
```

## 五、监控与运维

### 车端实时监控

```
车端 Telemetry → 云端 Dashboard:

实时监控:
  ├── 模型推理延迟 (P50, P95, P99)
  ├── 模型输出分布漂移 (Distribution Shift)
  ├── 安全事件 (AEB、ESA 触发次数)
  ├── 系统资源 (CPU/GPU/Memory 占用)
  └── 传感器健康状态 (LiDAR 脏污检测等)
```

### 分布漂移检测 (Distribution Shift Detection)

```
训练数据分布 vs 实际运行数据分布:

检测方法:
  1. 输入空间漂移: 图像的统计特征 (亮度/对比度直方图)
  2. 特征空间漂移: 模型中间层激活分布
  3. 输出空间漂移: 检测框数量/大小的分布变化

漂移告警 → 可能需要重新训练/微调
```

## 六、安全与合规

### OTA 安全

| 层面 | 措施 |
|------|------|
| **传输安全** | TLS 加密, CDN HTTPS |
| **包完整性** | 数字签名 (SHA-256 + 私钥) |
| **车端验证** | 验签 → 解密 → 安全启动验证 |
| **防重放攻击** | 时间戳 + Nonce |
| **权限管理** | 分级权限 (厂商/4S 店/用户) |
| **日志审计** | 完整 OTA 操作日志 |

### 合规要求

- **UN R156**：软件更新法规 (欧盟)
- **GB/T 标准**：中国 OTA 升级标准
- **OTA 升级必须可暂停/可回滚**
- **安全相关更新必须在规定时间内完成**

## 七、关键指标

| 指标 | 含义 | 华为 ADS 3.0 数据 |
|------|------|:--:|
| **迭代周期** | 模型新版本发布频率 | 每 5 天 |
| **OTA 成功率** | 成功更新 / 尝试更新 | > 99.5% |
| **更新包大小** | 每次 OTA 下载量 | - |
| **回滚时间** | 检测到问题→回滚完成 | < 1 秒 |
| **Canary 周期** | 灰度测试时长 | 24-72h |
| **安全事件率** | AEB 触发 / 千公里 | 持续下降 |
