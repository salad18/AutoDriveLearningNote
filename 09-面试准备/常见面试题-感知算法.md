# 常见面试题 — 感知算法

> 自动驾驶感知算法面试 20 道核心题，每题含 3-5 层面试官追问链。
> 能抗住 3 轮追问 = 拿到 Offer。

---

## 一、BEV 感知

### Q1: BEV 感知的核心思想？为什么要转到 BEV？⭐⭐

**核心回答**: BEV 将多视角 2D 图像特征变换到统一的鸟瞰坐标系。关键不是"换个视角"，而是**提供一个多传感器/多时序天然对齐的表示空间**。

**追问 1**: 既然 BEV 这么好，为什么之前不这么做？之前的技术瓶颈在哪？

之前做不到的原因：单目 2D→3D 是 ill-posed 问题（缺乏深度信息）。直到两件事发生：
1. **Transformer/Attention 机制成熟** (2020-): 可以通过 learnable query 隐式解决深度歧义，不需要精确深度
2. **大规模 3D 标注数据可用** (nuScenes 2019, Waymo 2020): 提供足够的监督信号

LSS (ECCV 2020) 是最早的突破，显式估计深度分布 → 投影 → BEV。但 LSS 依赖深度估计质量，BEVFormer (ECCV 2022) 的 Query 机制绕过了这个依赖。

**追问 2**: LSS、BEVFormer、PETR 三种范式的本质差异是什么？技术选择的 trade-off？

| 范式 | 深度处理 | 计算量 | 部署难度 | 精度上限 | 选型场景 |
|------|----------|--------|----------|----------|----------|
| LSS | 显式深度分布 | 中 | 低 (纯 Conv) | 中 | 追求部署效率 |
| BEVFormer | Attention隐式 | 高 (DeformAttn) | 高 (custom CUDA) | 高 | 追求精度 |
| PETR | 3D PE 隐式 | 中 | 中 | 中高 | 平衡 |

**追问 3**: 如果让你从零设计一个量产车的 BEV 感知方案，你选哪个？为什么？

我会选 LSS+BEVDepth 路线。量产车需要：10+ FPS 实时、低功耗芯片（Orin 30W）、可控延迟。
- LSS 是纯 Conv → TensorRT 加速成熟，INT8 量化稳定
- BEVDepth 的深度监督提升了 LSS 的弱点（深度不准），且不增加推理开销
- BEVFormer 的 Deformable Attn CUDA kernel 在端侧芯片上优化困难，2.5 FPS 不满足实时

但如果老板一定要 SOTA 精度（如 Robotaxi），我会选 BEVFormer v2 + ConvNeXt backbone。

**论文参考**: LSS (ECCV 2020 §3), BEVFormer (ECCV 2022 §3.2), PETR (ECCV 2022 §3.1)
**关键数值**: BEVFormer NDS=56.9 (2.5 FPS), BEVDet NDS=48.8 (15 FPS)

### Q2: BEVFormer 的 Spatial Cross-Attention 详解？⭐⭐⭐

**核心回答**: BEV Query 作为 Q，通过 Deformable Attention 在多尺度图像特征上采样。每个 Query 在 3D 空间定义 4 个高度的参考点 → 投影到 6 个相机 → 只关注投影点落在视野内的相机 → 每个有效相机采样 K=4 个点。

**追问 1**: Deformable Attention 的采样偏移 (offset) 是怎么学的？为什么能学到正确的采样位置？

```python
# 采样偏移是由 BEV Query 通过线性层预测的:
sampling_offset = Linear(bev_query)  # [B, N_q, n_heads*n_levels*n_points*2]
# 然后 reshape 为 [B, N_q, n_heads, n_levels, n_points, 2]

# 关键: 这不是随机偏移 — 参考点本身就是对正确位置的最佳先验
# 参考点 = BEV 3D 位置投影到图像 → 已经"非常接近"正确位置
# 偏移只需学习微小的修正: 矫正投影误差、对齐不同深度的特征
# 偏移量通常在 [-5, 5] pixels 范围内 (相对于参考点)
```

**追问 2**: K=4 真的够吗？如果物体很大，4 个采样点能覆盖吗？

K=4 是在 4 个特征层级上各取 1 个点，而不是总共 4 个。实际上：4 层级 × 4 采样点 × 8 头 = 每个 Query 关注 128 个不同位置。加上多尺度特征（低层看细节，高层看语义），对大多数物体足够了。但确实，大物体（如 bus 占 50+ BEV cells）在边缘 Query 处可能采样不到车身 → 需要多个相邻 Query 协作覆盖。

**追问 3**: 投影到相机的 3D 参考点，如果深度估计和实际差很多怎么办？

不需要精确深度！参考点的作用是**引导注意力去哪个图像区域看**，不是精确匹配。Attention 机制会自适应：
- 如果参考点偏了 → 采样 offset 会修正
- 如果该投影点完全不对 → attention weight 会降低 → 该相机的贡献变小
- 即使所有相机投影都不准，Temporal Self-Attention 的历史信息提供 fallback

这就是为什么 BEVFormer **不需要深度监督**，而 LSS 需要。

**追问 4**: CUDA 层面，Deformable Attention 是怎么实现的？为什么快？

标准 Attention 的问题不是计算量（FLOPS），而是显存带宽。每次 softmax 需要读写整个 attention matrix。Deformable Attention 的优化：
1. **Bilinear Interpolation**: 不需要矩阵乘法，只需要在特征图周围 4 个像素做双线性插值
2. **Memory Coalescing**: 相邻 Query 的采样点大概率在特征图的相近位置 → 访存合并
3. **Kernel Fusion**: mmdet3d 的 `deformable_attn_cuda` 将 offset 预测、双线性采样、加权求和融合到一个 CUDA kernel → 避免中间 tensor 的显存分配

**论文参考**: BEVFormer (ECCV 2022 §3.2.2, Eq.3-5)
**代码参考**: `mmdet3d/projects/BEVFormer/spatial_cross_attention.py`

### Q3: LSS (Lift-Splat-Shoot) 完整流程？⭐⭐⭐

**核心回答**:

```
Lift:  对每个像素 (u,v), 预测 D=128 维深度分布 → 特征 f_c × depth_dist → 3D Frustum特征
Splat: 利用相机内外参将 Frustum 坐标变换到 Ego 坐标系 → Sum Pooling 到 BEV grid
Shoot: BEV 特征 → ResNet BEV Backbone → 检测头
```

**追问 1**: 为什么 BEVDepth 要在 LSS 基础上加深度监督？LSS 的深度估计到底哪里不准？

LSS 的深度分布是**隐式学习**的 — 没有直接的深度真值，只靠检测 loss 反向传播来间接优化深度。问题：
1. **远处深度不可靠**: 远处物体的检测 loss 梯度弱 → 深度估计质量差
2. **遮挡区域**: 被遮挡的像素的深度分布会偏向近处（因为近处特征更"显眼"）
3. **重复纹理**: 如路面标线 → 深度分布模糊（多个深度峰值）

BEVDepth 的改进：利用 LiDAR 点云投影到图像生成稀疏深度真值 → 显式监督 DepthNet：
$$L_{depth} = \text{BCE}(d_{pred}, d_{gt\_from\_lidar})$$
消融实验：加深度监督后，NDS 提升 3.2 点，远处物体 AP 提升最显著。

**追问 2**: 深度分布维度 D=128 是怎么来的？D 越大越好吗？

D=128 是 nuScenes 的标准值（0-51.2m 范围，每 0.4m 一个 bin）。D 的影响：
- D=64: NDS 下降 ~1.5 点（远处深度分辨率不够）
- D=128: 标准配置
- D=256: NDS 提升 <0.5 点（边际收益递减，但计算量 ×2）
选择 D=128 的原因：0.4m 分辨率足以区分不同距离的物体; 再细粒度对检测精度帮助不大

**追问 3**: 视锥体特征的内存爆炸问题怎么解决？

每个像素 → D 维深度分布 → 视锥体特征 = C × D × H × W。
对 6 相机 × 640×960 × D=128 × C=256 = **~400GB** (FP32)。

解决方案（BEVDepth/BEVPoolv2）:
1. **延迟 Splat**: 不计算完整视锥体，只计算有效的 voxel indices
2. **BEVPoolv2**: 将 Voxel Pooling 用 CUDA kernel 加速 — 直接计算 3D 坐标 → BEV index → atomic add
3. **深度预过滤**: 将深度概率 < 0.01 的点直接丢弃 → 减少 90% 的计算
4. **Trick**: 用 `torch.sparse` 表示视锥体 → 只存非零元素

**论文参考**: LSS (ECCV 2020 §3), BEVDepth (AAAI 2023 §3.2), BEVPoolv2 (arxiv 2022)
**关键数值**: LSS D=128, BEVDepth NDS=56.5 (vs LSS-only NDS=~48)

### Q4: PETR 的 3D Position Encoding 设计？为什么不需要显式 BEV？⭐⭐⭐

**核心回答**: PETR 的核心洞察 — **不需要构造显式的 BEV 特征图，只需要让图像特征"感知到"自己的 3D 位置，再通过 Transformer Decoder 直接输出 3D 检测结果**。

**追问 1**: PETR 的 3D PE 是怎么生成的？完整推导。

```python
# Step 1: 在 3D 空间中定义 anchor points (如立体网格)
# 范围: [-51.2, 51.2] × [-51.2, 51.2] × [-5, 3]
# 网格: 128×128×8 个 anchor points

# Step 2: 将每个 anchor point 投影到每个相机
# P_3d = (x, y, z) → P_2d = project(K, [R|t], P_3d)
# 只保留落在图像内的投影点

# Step 3: 对 2D 坐标进行 positional encoding
PE_3D = MLP(concat([
    sin/cos(P_2d_x),  # 水平位置
    sin/cos(P_2d_y),  # 垂直位置
    sin/cos(x),       # 3D 世界坐标 (可选)
    sin/cos(y),
    sin/cos(z)
]))
# Shape: [N_cam, H, W, C]
```

**追问 2**: PETR 和 BEVFormer 的本质区别？为什么 PETR 不需要 Temporal Attention？

PETR 的 Object Query 直接从图像特征 + 3D PE 解码出 3D box，不需要构造 BEV 空间。时序信息在 PETRv2 中通过**对前帧的 3D 坐标加时序编码**来隐式融合 — 不需要 warp/align，更高效但不是那么显式。

BEVFormer 必须构造 BEV 空间因为它的 Spatial Cross-Attention 依赖 BEV grid 结构。

**追问 3**: PETR 的劣势是什么？什么时候选 PETR 不选 BEVFormer？

劣势：
1. 3D PE 的 anchor points 是固定的 → 远距离区域采样密度不够
2. 没有显式 BEV → 下游任务（地图、占据）需要额外网络
3. 对多尺度特征利用不如 BEVFormer 充分

选 PETR 的场景：只需要 3D 检测，不需要 BEV 分割/地图 → PETR 更高效。

**论文参考**: PETR (ECCV 2022 §3.1 Eq.4-7)
**关键数值**: PETR NDS=50.4, PETRv2 NDS=58.2 (StreamPETR NDS=63.7)

### Q5: BEVDet vs BEVFormer — 实际选型怎么选？⭐⭐

**核心回答**: 看场景。

| 场景 | 选型 | 理由 |
|------|------|------|
| **量产车** | BEVDet | 纯 Conv → TensorRT 优化成熟, 15 FPS, INT8 稳定 |
| **Robotaxi** | BEVFormer | 精度优先, 可以接受更低 FPS |
| **需要时序** | BEVDet4D or BEVFormer | BEVDet 需要额外的 4D 扩展 |
| **多任务** | BEVFormer | BEV 特征可直接用于检测+分割+地图 |

**追问 1**: TensorRT 部署时，BEVDet 和 BEVFormer 的核心差距是什么？

BEVDet (纯 Conv):
```python
# ONNX 导出: Conv+BN+ReLU → 一键融合
# TRT优化: Layer fusion + INT8校准 + kernel auto-tuning → 10-15 FPS on Orin
```

BEVFormer (Deformable Attention):
```python
# 问题: deformable_attn 不是标准 ONNX op → 需要自定义 plugin
# 自定义 plugin 的 TRT 优化远不如标准 Conv → 量化后精度损失大
# 实测: Orin上量化后推理 3-5 FPS, FP16精度损失 2-3 NDS
```

**追问 2**: BEVDet4D 的时序怎么做的？和 BEVFormer 的 Temporal SA 有什么不同？

BEVDet4D: 将上一帧对齐后的 BEV 特征 **直接 concat** 到当前帧 BEV → 3D Conv 融合。
BEVFormer: 用 **Self-Attention** 融合（Q=当前, K/V=历史）。

区别：
- BEVDet4D 融合是隐式的（3D Conv 中的 receptive field）→ 简单但不够精准
- BEVFormer 融合是显式的（attention weights 可解释）→ 精准但慢
- 实测：BEVDet4D 加时序 NDS +2.5, BEVFormer 加时序 NDS +3.6 → 差距不大

**论文参考**: BEVDet (2022), BEVDet4D (2022), BEVFormer (ECCV 2022)

### Q6: 时序融合方式对比 — 显存/计算量/精度 trade-off？⭐⭐⭐

| 方式 | 显存 | 计算量 | 精度 | 代表工作 |
|------|------|--------|------|----------|
| **concat** | ~2× | +30% | +2.5 NDS | BEVDet4D |
| **Transformer SA** | ~1.2× | +50% | +3.6 NDS | BEVFormer |
| **Recurrent** | ~1× (固定) | +20% | +2.0 NDS | SOLOFusion |
| **3D Conv** | ~1.5× | +25% | +2.8 NDS | UVTR |

**追问**: 如果有无限算力，哪种方式理论上最好？

理论上 **Transformer SA + 多帧 (4+ frame)** 最好，因为 SA 能学习任意时序依赖。但实际中，3 帧以上的边际收益递减（因为远帧信息被 ego-motion 退化）。目前 StreamPETR 用 recurrent + 长时序取得了最好的结果 (NDS=63.7)，证明 **recurrent 机制在长时序上的信息保持能力** 优于 Transformer SA。

## 二、3D 检测 & 占据网络

### Q7: CenterPoint 核心思想？为什么用 center-based？⭐⭐⭐

**核心回答**: CenterPoint 将 3D 检测转化为关键点估计问题 — 在 BEV 平面上预测每个位置是目标中心的概率 (heatmap) + 回归 3D box 属性。

**追问 1**: anchor-based 和 center-based 的根本区别？

| | Anchor-based | Center-based |
|---|---|---|
| **先验假设** | 需要预设 anchor 尺寸/朝向 | 无先验 |
| **正负样本** | IoU > 0.5 为正 | Gaussian heatmap 峰值附近为正 |
| **后处理** | NMS (需要!) | heatmap peak → 不需要 NMS |
| **对罕见尺寸的泛化** | 差 (trailer, construction) | 好 |
| **训练复杂度** | 高 (大量 anchor 正负匹配) | 低 |

**追问 2**: heatmap 上的高斯核 σ 是怎么选的？为什么不用 one-hot peak？

```python
# 不是 one-hot！在目标中心 (x,y) 处放一个 2D Gaussian:
heatmap[x, y] = exp(-((x-x_c)² + (y-y_c)²) / 2σ²)

# σ 的选择:
# σ = object_size / 2.5 (经验值)
# Car (2m宽): σ ≈ 0.8 cells (在 0.5m grid下)
# Pedestrian (0.5m): σ ≈ 0.2 cells

# 为什么用 Gaussian 而不是 one-hot?
# 1. 即使是 GT 中心也有标注噪声 → soft label 更鲁棒
# 2. 相邻 grid cell 如果预测到同一个目标 → Gaussian 的 overlap 使它们不会互相排斥
# 3. 训练更稳定：Focal Loss 在 one-hot 下梯度太稀疏
```

**追问 3**: CenterPoint 的 NDS 能到什么水平？和检测头有关吗？

CenterPoint-Pillar (voxel=0.2m): NDS=65.5, mAP=60.3 (单帧 LiDAR)
加多帧 LiDAR: NDS=67.3, mAP=61.8

**检测头不是瓶颈** — 瓶颈是 backbone（点云稀疏性）和时序信息。最好的 CenterPoint 变体 (TransFusion) 将图像特征作为辅助 → NDS 可到 71+。

**论文参考**: CenterPoint (CVPR 2021 §3.1-3.2)
**代码参考**: `OpenPCDet/pcdet/models/dense_heads/center_head.py`

### Q8: Occupancy Network 和 3D 检测的核心区别？⭐⭐⭐

**核心回答**: 3D 检测输出**物体级别**的 BBox (稀疏表示)，占据网络输出**体素级别**的占据状态+语义 (稠密表示)。占据网络回答了"空间的每个位置是被什么占据的"，而检测只回答了"有哪些物体，在哪"。

**追问 1**: 既然有 3D 检测了，为什么还需要占据网络？

因为检测的本质缺陷：**只能检测训练集见过的类别**。现实世界有：
- 异形障碍物: 散落的货物、倒下的树木、施工的水马
- 不规则物体: 挂车 (trailer 无固定尺寸)、开放式车厢
- 负空间: 悬空的管道、桥洞 (检测会认为是障碍物，占据能判断高度)

占据网络通过**几何先验** (空间被占 vs 空闲) 弥补检测的语义局限性。

**追问 2**: Occ3D 数据集怎么构建的？标注成本高吗？

Occ3D 基于 nuScenes 构建：
1. 利用 LiDAR 点云 (稀疏) + 连续帧累积 → 稠密化
2. 利用 nuScenes 的 3D box 标注 → 物体内部的 voxel 赋语义
3. 插值/补全 → 未观测到的区域标记为 "unknown"
4. 总计: 700 scenes × 200×200×16 voxels × 17 classes

标注成本远低于人工标注（因为大量自动化），但稠密化过程引入了插值噪声。

**追问 3**: Tesla Occupancy Network 和 Occ3D 的区别？

| | Occ3D (学术界) | Tesla ON (工业界) |
|---|---|---|
| **输入** | 单帧 6 相机 | 视频序列 (8 camera × N frames) |
| **输出** | 语义占据 (17类) | 占据 + 流速 (flow) + 不确定度 |
| **分辨率** | 0.4m voxel | ~0.2m voxel (推测) |
| **训练数据** | nuScenes (公开) | 自采数据 (海量, 不公开) |
| **目标** | Benchmark | 替代 HD Map 做规划 |

**论文参考**: Occ3D (NeurIPS 2023), SurroundOcc (ICCV 2023)

### Q9: NDS 指标的构成？为什么 mAP 权重是 5？⭐⭐

$$NDS = \frac{1}{10}[5 \cdot mAP + \sum_{i} (1 - \min(1, mTP_i))]$$

5 个 True Positive 误差指标 (mTP): mATE (平移), mAOE (朝向), mASE (尺度), mAVE (速度), mAAE (属性)。

**追问**: 为什么 mAP 权重是 5 而不是其他数？

因为 nuScenes 官方认为**检测精度 (mAP) 的重要性是每个质量指标 (TP metrics) 的 5 倍**。一个检测器：
- 如果 mAP 很高但定位很差 → 在实际中无用
- 如果定位完美但 mAP 很低 → 漏检太多

5 的权重是经验选择，在 nuScenes challenge 的实践中证明能选出既有高精度又有好定位的检测器。

注意陷阱：NDS 会**对超过 1.0 的 mTP 截断** (`min(1, mTP)`)，意味着如果某个 TP 指标已经很好（< 1m 误差），进一步改善对 NDS 无贡献 → 引导资源到最差的指标上。

## 三、Transformer & 架构

### Q10: Self-Attention 计算复杂度和显存 — 实战估算？⭐⭐⭐

**标准推理**: O(N²d) 计算 + O(N²) 显存。

**追问 1**: BEVFormer 在 8×A100, batch_size=1, BEV=200×200 下，显存占用多少？逐项算。

```
N_bev = 200×200 = 40000, d=256, FP16:

1. 模型参数: 68.4M × 2 bytes = 137 MB
2. 梯度 (训练时): 68.4M × 2 bytes = 137 MB
3. 优化器 (Adam FP32): 68.4M × 8 bytes = 547 MB

4. BEV Queries: 1×40000×256×2bytes = 20.5 MB × 6 layers × 2 (前向+反向)≈ 246 MB

5. 图像特征 (6 cameras, 1/8 scale):
   ~6 × (80×120×256) × 4 levels × 2bytes ≈ 472 MB

6. Deformable Attn 中间变量:
   reference_points + sampling_offsets + attn_weights
   ≈ 40000 × 8 × 4 × 4 × 2 × 2bytes × 6 layers ≈ 62 MB

7. Temporal BEV 历史: 40000×256×2bytes = 20.5 MB

总计 ≈ 137 + 137 + 547 + 246 + 472 + 62 + 20 ≈ 1621 MB ≈ 1.6 GB

这是理论下限。实际 PyTorch overhead (CUDA context, allocator fragmentation)
会使实际显存 ≈ 2-3× 理论值 ≈ 3-5 GB per GPU。
```

**追问 2**: 如果 N_bev=40000，标准 Attention 的 attention matrix 多大？为什么不可行？

$40000^2 \times 2$ bytes (FP16) = 3.2 GB — 仅 attention matrix。加上 8 头 = 25.6 GB，超过 A100 的 80GB 中的一大半。而且每次 softmax 需要读写整个 matrix。

### Q11: Deformable Attention 的实际加速比？⭐⭐

**理论上**: O(N²) → O(NK) = 40000²/40000×4 = 10000x。

**追问**: 实际加速为什么远不到理论值？

1. Deformable Attention 需要额外的计算: offset 预测 (Linear)、双线性插值、多层级聚合 — 这些是标准 Attention 没有的
2. 双线性插值是随机访存 (non-coalesced)，cache 命中率低
3. Kernel launch overhead: 相比标准 Attention 的一个大矩阵乘法，Deformable 有更多的小 kernel
4. 实测: 约 5-15x 加速 (不是 10000x)，但显存节省接近理论 (~100x)

### Q12: LayerNorm vs BatchNorm — 实战选择？⭐⭐

| | BN | LN |
|---|---|---|
| **归一化轴** | (N, H, W) → per channel | (C, H, W) → per sample |
| **序列建模** | 需要 padding mask | 天然适配 |
| **小 batch** | 不稳定 | 稳定 |
| **推理** | 用 running stats ≠ 训练 | 训练 = 推理 |

**追问**: Transformer 推理时 LayerNorm 怎么做的？和训练有什么区别？

```python
# 训练和推理完全一致！这是 LN 相比 BN 的一大优势:
def layernorm(x, gamma, beta, eps=1e-5):
    mean = x.mean(dim=-1, keepdim=True)  # 每个样本独立
    var = x.var(dim=-1, unbiased=False, keepdim=True)
    x_norm = (x - mean) / torch.sqrt(var + eps)
    return gamma * x_norm + beta

# 不需要 running_mean/running_var → 训练=推理
# 不需要区分 train/eval mode
```

### Q13: Flash Attention 为什么快？⭐⭐⭐

**核心**: 不是减少 FLOPS，是减少 HBM 读写。

```
标准 Attention 的显存操作:
  S = QK^T  → 写 HBM: O(N²)
  P = softmax(S) → 写 HBM: O(N²)  
  O = PV → 写 HBM: O(Nd)
  总计 HBM 读写: ~O(N²)

Flash Attention:
  将 Q,K,V 分块 (tile size = B_r × B_c)
  每块在 SRAM 中完成 QK^T + softmax + ×V
  只在块边界时才写回 HBM
  总计 HBM 读写: O(N²d²/M) ≈ O(N√d)
  
  A100: M(SRAM) = 192KB per SM → 显著减少 HBM 往返
```

**追问**: 实际加速多少？什么场景下效果最好？

- 短序列 (N<512): 加速 <1.5x (瓶颈在计算, 不在 IO)
- 中序列 (N=1K-4K): 加速 2-4x (IO 和计算平衡)
- 长序列 (N>8K): 加速 5-8x (IO 是主要瓶颈)
- BEVFormer 中: 约 1.3-1.8x (N=40000 但 attention 是局部的 Deformable, IO 瓶颈不严重)

## 四、训练与工程

### Q14: AMP 混合精度训练 — Loss Scaling 的实际问题？⭐⭐⭐

**追问**: 你训练时遇到过 loss scaling 不断减小的情况吗？怎么处理？

遇到过。`GradScaler` 的动态 scale 机制：
```
scale 初始值: 2^16 = 65536
如果连续 N 步无 inf/nan → scale × 2 (增长期)
如果有 inf/nan → scale / 2 (缩减期) + 跳过该步更新
```

如果 scale 一直下降 → 说明梯度一直在溢出 → 常见原因：
1. LR 太大 → 梯度爆炸
2. 数据异常 (NaN in input)
3. FP16 敏感的层 (depth estimation, exp, large logits) → 把这些层改为 FP32
4. 解决: 保持 FP32 的层: LayerNorm, Softmax, 深度估计 Head

### Q15: DDP vs FSDP (ZeRO-3) — 通信开销分析？⭐⭐⭐

**追问**: 为什么 8 卡 FSDP 不是线性加速 8×？通信开销有多大？

```
DDP (8 GPU): 
  只 all-reduce 梯度: 2 × gradient_size × (N-1)/N ≈ 1.75 × gradient_size

FSDP ZeRO-3 (8 GPU):
  每次 forward: all-gather 参数分片 → 通信 N-1/N × param_size/GPU
  每次 backward: reduce-scatter 梯度 → 通信
  额外: 参数分片的 all-gather 是在每个 layer 都发生的
  
  总通信量 ≈ DDP 的 1.5-2× (取决于模型结构)
  
  BEVFormer 68M 参数:
  梯度 = 68M × 2 bytes = 136 MB
  DDP all-reduce: ~238 MB 通信量
  FSDP: ~350-500 MB 通信量
  在 NVLink 600 GB/s 下: 通信时间 ~0.4-0.8 ms per layer
  在 PCIe 32 GB/s 下: 通信时间 ~10-15 ms per layer (显著瓶颈!)
  
  所以 8 GPU × PCIe → 实际加速 ≈ 5-6× (不是 8×)
  8 GPU × NVLink → 实际加速 ≈ 7-7.5× (接近线性)
```

### Q16: 多任务联合训练的梯度平衡？⭐⭐⭐

**追问**: Uncertainty Weighting 的 σ 学习过程是怎样的？

```python
# Kendall et al. 的 Uncertainty Weighting:
# 总 loss = Σ 1/(2σ_i²) * L_i + log(σ_i)

# 行为分析:
# σ 小 → 1/(2σ²) 大 → 该任务 loss 权重大 (模型对该任务有信心)
# σ 大 → 1/(2σ²) 小 → 权重大 → 但 log(σ) 惩罚大 → 防止 σ 无限大

# 实际上 σ 的行为取决于任务难度:
# 简单任务 (如 car detection): σ → 小值 (0.1-0.5) → 高权重
# 困难任务 (如 planning): σ → 大值 (1-3) → 低权重

# 问题: 这会导致容易的任务慢慢主导训练
# 改进: 对 σ 设置 lower bound (如 σ > 0.2) 防止权重爆炸
```

**GradNorm 替代方案**: 监控每个任务的梯度范数变化率 → 动态调整权重 → 使所有任务以相似速度学习。

## 五、端到端

### Q17: UniAD — TrackFormer 的匹配算法？⭐⭐⭐

**追问**: 为什么不用简单的匈牙利匹配？

UniAD 的 TrackFormer 不做显式匹配！它的核心设计是 **Track Query 自带时序一致性**：

```python
# 标准方法: Detect → Hungarian Match → Assign Track ID
# UniAD: Track Query 在时序中持续存在，隐式携带 ID

# 每帧:
# 1. 上一帧的 Track Queries + 新 Detect Queries → Self-Attention 交互
# 2. 通过 Attention 自适应决定: 哪些 Track Query 继续跟踪、哪些消失、哪些新的出现
# 3. 输出: Track Query 直接预测 bbox + velocity

# 优势: 不需要显式 matching threshold (IoU 阈值 → 不需要调参!)
# 问题: Track Query 数量是固定的 → 不能处理任意数量目标 → 需要冗余 query
```

### Q18: 端到端 vs 模块化 — 事故后怎么 debug？⭐⭐⭐

**追问**: 如果端到端模型发生事故，你怎么排查？

这是端到端模型的最大痛点。排查思路：
1. **特征可视化**: 可视化中间层 attention map → 看模型在事故时刻"看着"哪里
2. **模块 probe**: 在训练好的端到端模型上加 probe classifiers (det head, seg head) → 不用梯度，只 forward → 看各中间表示的检测/分割质量
3. **反事实分析**: 修改输入 (去掉某个相机、mask 某个物体) → 观察规划输出变化 → 定位关键依赖
4. **影子模式**: 端到端模型不上线控制，只在后台跑 → 对比人类驾驶员的差异 → 积累 bad case
5. **分体式兜底**: 最新的趋势 (华为 GOD+PDP) — 端到端做决策 + 规则做安全兜底 → 至少知道"哪里违反了规则"

## 六、部署

### Q19: TensorRT INT8 量化 — 敏感层分析？⭐⭐⭐

**追问**: INT8 量化后的精度损失怎么评估和修复？

```
量化流程:
1. 校准: 用 100-500 张代表性图像跑 forward → 收集每层的 activation range
2. 量化: weights + activations → INT8
3. 评估: 对比 FP32 baseline 和 INT8 的 NDS/mAP

敏感层定位:
- FP32 vs INT8 output 逐层对比 → 找出 MSE 最大的层
- 常见敏感层:
  a. 第一个 Conv (直接处理 raw image → feature range 差异大)
  b. FPN 的 top-down path (小分辨率特征 + 大分辨率特征融合)
  c. Detection head 的最后一层 (分类 logits → 对精度极敏感)
  d. BEV 的 depth estimation head

修复:
- 敏感层保持 FP16 (部分量化)
- 用 QAT (Quantization-Aware Training): 在训练时模拟量化 → 模型自适应
- 调整校准数据集 (确保覆盖边缘场景: 夜间/雨天)
```

### Q20: 数据漂移 (Data Drift) 怎么发现和解决？⭐⭐⭐

**追问**: 你实际遇到过吗？怎么量化的？

典型场景：模型在城市 A (深圳) 训练 → 部署到城市 B (北京)。
- 北京有更多的立交桥、更宽的马路、不同的交通标志
- Detection mAP 从 48 降到 42 → 6 点的漂移

量化方法：
1. **输入分布对比**: 计算两地的 image statistics (mean, std per channel) → KL divergence
2. **特征分布对比**: 用训练集和在线数据的 backbone features → 做 t-SNE 可视化 → 看是否形成 cluster gap
3. **类别分布**: 北京的 truck/bus 比例远高于深圳 → class distribution shift

解决：
- 采集北京数据 → 标注 → 混入训练集 (30% 新数据 + 70% 旧数据)
- LoRA 微调 (只训 2% 参数) → 让模型适配北京的特征分布
- 持续学习: 定期用新数据更新 running BN stats

## 七、手写算法：匈牙利匹配 & Label Assignment (P0 新增)

### Q21: 手写匈牙利算法 (Hungarian Algorithm) ⭐⭐⭐⭐

```python
import numpy as np
from scipy.optimize import linear_sum_assignment

def hungarian_matching(cost_matrix):
    """
    cost_matrix: [N_det, N_gt] — 每个 pred 配每个 gt 的 cost
    返回: (row_indices, col_indices) — 匹配对
    """
    # 使用 scipy 的优化实现 (O(n³))
    row_ind, col_ind = linear_sum_assignment(cost_matrix)
    return row_ind, col_ind


# 如果不让用 scipy，手写匈牙利 (简化版, O(n³)):
def hungarian_manual(cost_matrix):
    """
    简化实现 — 核心思路:
    1. 行规约: 每行减去最小值
    2. 列规约: 每列减去最小值
    3. 用最少线覆盖所有 0 → 如果线数 = n → 找到最优匹配
    4. 否则 → 调整矩阵 → 重复
    """
    n, m = cost_matrix.shape
    assert n <= m  # Ensure square or pad
    
    # Step 1 & 2: Row and column reduction
    cost = cost_matrix.copy()
    cost -= cost.min(axis=1, keepdims=True)
    cost -= cost.min(axis=0, keepdims=True)
    
    # Step 3 & 4: Find optimal assignment (simplified)
    # In practice, use scipy — 手写只是为了展示理解
    # interview中: 解释算法思路 + 时间/空间复杂度 + 为什么用它
    pass

# 面试正确回答: "匈牙利算法是 O(n³), 用于 DETR 的 set prediction loss
# 中的 bipartite matching。我实践中直接用 scipy.optimize.linear_sum_assignment,
# 但理解其原理是: 在 cost matrix 中找到总 cost 最小的完美匹配。"
```

**追问: 为什么 DETR 用匈牙利而不是贪心匹配?**

贪心: 每次选 cost 最小的 pair → 移除 → 重复。O(n² log n)，快但不保证全局最优。

匈牙利: 全局最优匹配。对于 DETR，每个 GT object 必须分配恰好一个 prediction → 贪心可能把"第二好的 GT 匹配给了第一个 pred，导致更好的 pred 没 GT 可匹配"→ 匈牙利避免了这种情况。

**追问: DETR 训练早期为什么收敛慢？**

三个原因:
1. **二分图匹配不稳定**: 训练初期，匈牙利匹配的结果每个 epoch 都在变 → 同一个 object query 今天匹配车明天匹配行人 → 学习信号混乱
2. **Cross-Attention 学习慢**: Object query 需要学会"去图像的哪个位置看"→ 这是 hard attention，收敛比 soft attention 慢
3. **解决方案**: Deformable DETR (用参考点引导 attention → 更快), DN-DETR (加去噪 query → 稳定匹配)

## 八、深度估计方案横向对比 (P1 新增)

> 面试官必问：「单目深度估计是 ill-posed 问题，各方案怎么解决的？」

| 方案 | 深度处理方式 | 是否需要深度真值 | 深度估计精度 | 代表模型 |
|------|------------|:---:|:---:|------|
| **LSS** | 隐式学习 (detection loss 间接监督) | 否 | 中 (远处不准) | BEVDet |
| **BEVDepth** | 显式监督 (LiDAR 投影 sparse GT) | **是** (LiDAR) | 高 | BEVDepth |
| **BEVFormer** | Attention 隐式 (query 学采样位置) | 否 | 中高 | BEVFormer |
| **BEVStereo** | 双目匹配 (stereo matching → depth) | 否 | 高 (近距) | BEVStereo |
| **SOLOFusion** | 长程+短程深度估计融合 | 部分 | 最高 | SOLOFusion |
| **PETR** | 3D PE 绕过深度 (不看深度!) | 否 | N/A | PETR |

**追问: 为什么 PETR 可以绕过深度？**

PETR 不给每个像素分配深度，而是给每个 anchor point 提供 3D 位置 → Transformer 在 3D 空间中做 attention → 物体的 3D 位置由 attention weights 隐式学习 → 不需要显式深度。

代价: 没有显式深度 → 在遮挡和远距离的 3D 定位精度不如 BEVDepth (后者有硬深度监督)。

## 九、时序建模全面对比 (P1 新增)

> 面试官必问：「LSTM/3DConv/Transformer/Recurrent — 选哪个？」

| 方法 | 显存 | 计算量 | 精度提升 | 长时依赖 | 代表工作 |
|------|:---:|:---:|:---:|:---:|------|
| **Concat + 3D Conv** | ~2× | +30% | +2.5 NDS | 差 (>3帧退化) | BEVDet4D |
| **Transformer SA** | ~1.2× | +50% | +3.6 NDS | 中 (≤3帧) | BEVFormer |
| **Recurrent (Memory)** | ~1× | +20% | +4.0 NDS | **好** (8+帧) | StreamPETR |
| **LSTM/GRU** | ~1× | +15% | +2.0 NDS | 中 | 早期工作 |
| **Temporal PE** | ~1× | +10% | +1.5 NDS | 差 (1帧) | PETRv2 |

**选型决策**:

```
如果你的延迟预算充裕 + 只需要短时序 (≤3帧):
  → Transformer Self-Attention (BEVFormer)
  优势: 自适应融合, 可解释 (attention weights)

如果你需要长时序 (5+帧) + 显存紧张:
  → Recurrent Memory Queue (StreamPETR)
  优势: 固定显存, 长时依赖, 当前 SOTA

如果你追求部署简单:
  → Concat + 3D Conv (BEVDet4D)
  优势: TensorRT 优化最成熟

如果你要设计一个新框架:
  → Recurrent (StreamPETR 风格) + FlashAttention
  优势: 兼顾效率和精度, 2024 年趋势
```

## 十、当前技术方向 (2024-2025)

### 7.1 BEV → BEV+Occupancy 融合

纯 BEV 的局限性在 2024 年已经很明显：不规则的障碍物 (施工区、散落物) 无法用 BBox 表示。

**趋势**: 几乎所有量产方案都在从 BEV Detection → BEV + Occupancy 双输出。代表：华为 GOD (ADS 3.0)、理想 OCC、小鹏 XNet 2.0。

### 7.2 端到端 vs 分体式

2024 年的共识：**纯黑盒端到端 (UniAD-style) 不适合量产**，分体式端到端 (华为 GOD+PDP) 更务实。

| | 纯端到端 | 分体式端到端 |
|---|---|---|
| **可解释性** | 差 | GOD 输出可解释占据，PDP 输出可解释轨迹 |
| **安全兜底** | 难 | 规则兜底 + 端到端决策并行 |
| **迭代速度** | 慢 (需要全量重训) | 快 (模块独立优化) |
| **代表** | UniAD, VAD, GenAD | 华为 GOD+PDP, Wayve GAIA+LINGO |

### 7.3 VLM (Vision-Language Model) 进入驾驶

DriveVLM (2024), LINGO-2 (Wayve 2024) 将语言作为驾驶理解的桥梁：
- 自然语言描述场景 → "前方有行人正在过马路，左侧有车变道"
- 语言作为 intermediate representation → 可解释、可编辑
- 但仍处于 research stage → 推理延迟 (1-3s) 不足以实时控制

### 7.4 World Model 用于闭环仿真

GAIA-1 (Wayve, 2023) → DriveDreamer-2 (2024) → 生成逼真的驾驶视频用于训练。
2024-2025 趋势：World Model + RL — 在虚拟世界中让模型通过强化学习自我进化。

### 7.5 矢量化 vs 密集表征的战争

VAD, MapTRv2 证明了矢量表征的高效性。2024 年越来越多的方案在感知层输出矢量化结果 (agent tracks, lane graphs)，规划层直接消费矢量 → 大幅减少计算量。
