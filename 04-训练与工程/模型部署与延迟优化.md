## 〇、大白话总览

### 部署的本质：延迟 vs 精度的拔河

```
车端算力固定（Orin 等芯片）
  ↓
模型越大越准 → 但越慢 → 可能撞车（反应不过来）
模型越小越快 → 但越差 → 可能撞车（看不见）
  ↓
部署工程师的工作：在"算力预算"内，找到精度损失最小的方案
```

**延迟预算**：从传感器看到东西到车做出反应，总预算 ~150ms。模型推理只是其中一段（约一半），剩下是传感器、预处理、规划、控制的固定开销。

> [!note] 打个比方
> 部署像"搬家进小户型"：家具（模型）很全，但屋子（芯片算力）就那么大。要么换小家具（轻量模型）、要么拆掉重装（TensorRT 优化）、要么放弃一些家具（降分辨率/量化）——**目标是"住得下且不砸脚"（延迟达标且精度可接受）**。

## 一、延迟预算 (Latency Budgeting)

### 1.1 典型自动驾驶延迟链路

```
传感器曝光 → 数据传输 → 预处理 → 模型推理 → 后处理 → 跟踪 → 预测 → 规划 → 控制
   10ms        5ms        5ms       ???        5ms     5ms     20ms    20ms    5ms

模型推理预算 = 150ms - 75ms (固定开销) = 75ms

BEV 检测模型必须在 75ms 内完成!
```

> [!note] 为什么"固定开销"这么重要？
> 传感器曝光（10ms）+ 传输（5ms）+ 预处理（5ms）+ 后处理（5ms）+ 跟踪（5ms）+ 预测（20ms）+ 规划（20ms）+ 控制（5ms）= 75ms **是动不了的**（物理和系统开销）。模型推理只能分剩下的 75ms。**面试回答延迟问题第一步：先算固定开销，再给模型预算**——这个框架本身就展示系统性思维。

### 1.2 分模块时间分析

```python
# 用 profiler 或 nsys 分析实际推理时间:
# 假设目标: 75ms total on Orin (INT8)

BEV 检测模型延迟拆解:
┌─────────────────────────┬──────────┬──────────┐
│ 模块                     │ 时间(ms) │ 占比     │
├─────────────────────────┼──────────┼──────────┤
│ Image Backbone (6 cam)  │ 28       │ 37%      │
│ FPN Neck                │ 8        │ 11%      │
│ View Transform (LSS)    │ 18       │ 24%      │
│ BEV Encoder             │ 12       │ 16%      │
│ Detection Head          │ 5        │ 7%       │
│ NMS 后处理              │ 4        │ 5%       │
├─────────────────────────┼──────────┼──────────┤
│ Total                   │ 75       │ 100%     │
└─────────────────────────┴──────────┴──────────┘
```

**优化优先级**: Backbone (37%) > View Transform (24%) > BEV Encoder (16%)

> [!warning] 优化的第一原则：**先测后砍，砍大头**
> 不要凭感觉优化——先用 profiler（[[AI-Infra详解]] 第六节）测出每个模块的真实耗时。**37% 的 Backbone 和 5% 的 NMS，投入同样的精力，收益差 7 倍**。二八法则在延迟优化里极其明显。

### 1.3 必须降到 50ms — 砍哪里？

```
砍 25ms 的方案 (面试展示系统性思考):

方案 A: 换轻量 Backbone (最大收益)
  ResNet-50 → EfficientNet-B0 / MobileNetV3
  延迟: 28ms → 12ms (-16ms)
  精度损失: NDS -1.5
  ⚠ 风险: 特征表征能力下降 → 后续模块也受影响

方案 B: 降分辨率 (最安全)
  输入: 1600×900 → 800×450
  Backbone: 28ms → 10ms (-18ms)
  精度损失: NDS -2.0 (主要是小物体)
  ✅ 优势: 所有模块都加速, 不需要改模型结构

方案 C: 减少 BEV 网格 (深层加速)
  200×200 → 128×128
  BEV Encoder: 12ms → 5ms (-7ms)
  View Transform: 18ms → 9ms (-9ms)
  精度损失: NDS -1.5 (大物体影响小, 小物体定位模糊)
  ✅ 优势: 线性节省显存

方案 D: 去掉 NMS (后处理优化)
  center-based head (CenterPoint) → 不需要 NMS
  延迟: -4ms
  精度: 基本无损 (CenterPoint 本身就不需要 NMS)

推荐组合: B + D (降分辨率 800×450 + CenterPoint head)
  → 总延迟: ~42ms
  → 精度损失: NDS -2.0
  → 可通过更好的 backbone (EfficientNet-B3) 补偿 ~1.0 NDS
```

> [!note] 读四个方案的"决策框架"（面试展示系统思考）
> - **A 换 Backbone**：收益大但影响全局（特征质量下降，下游全受影响）。
> - **B 降分辨率**：最安全（不动结构，所有模块都加速），但小物体受影响最大。
> - **C 缩 BEV 网格**：深层加速（视图变换+BEV 编码器都受益），线性省显存。
> - **D 去 NMS**：几乎无损的"白捡"（CenterPoint 本身不需要 NMS）。
> **推荐 B+D 组合**：安全（不动结构）+ 白捡（去 NMS），精度损失用更好的 backbone 补偿——**"组合拳 + 补偿"是标准答案结构**。

## 二、TensorRT 深度优化

### 2.1 标准优化流程

```bash
# Step 1: PyTorch → ONNX
python export_onnx.py --model bevdepth --input 800x450

# Step 2: ONNX → TensorRT Engine
trtexec \
  --onnx=model.onnx \
  --saveEngine=model_fp16.trt \
  --fp16 \
  --workspace=4096 \
  --minShapes=input:1x3x450x800 \
  --optShapes=input:4x3x450x800 \
  --maxShapes=input:8x3x450x800

# Step 3: INT8 校准
trtexec \
  --onnx=model.onnx \
  --saveEngine=model_int8.trt \
  --int8 \
  --calib=calibration_cache.bin
```

> [!note] 三步流程的本质
> **PyTorch（训练框架）→ ONNX（通用中间格式）→ TensorRT Engine（硬件专用优化）**。TensorRT 会做算子融合（Conv+BN+ReLU 合并成一个 kernel）、kernel 自动调优（选最快的实现）、精度选择（FP16/INT8）。**`--minShapes/optShapes/maxShapes` 是动态 batch 的优化空间**——TensorRT 按 opt 形状优化，实际推理在 min-max 之间用。

### 2.2 INT8 量化 — 逐层精度分析

```python
# 量化后逐层对比 FP32 vs INT8 输出差异
def analyze_layer_sensitivity(model_fp32, model_int8, calib_data):
    sensitivities = {}

    for name, layer_fp32, layer_int8 in zip_layers(model_fp32, model_int8):
        # 跑同一 batch
        out_fp32 = layer_fp32(input_data)
        out_int8 = layer_int8(input_data)

        # 计算 MSE
        mse = F.mse_loss(out_fp32.float(), out_int8.float())
        sensitivities[name] = mse.item()

    # 排序 → 找出 Top-5 敏感层
    return sorted(sensitivities.items(), key=lambda x: x[1], reverse=True)[:5]

# 典型敏感层排名 (BEVDet on nuScenes):
# 1. depth_net.last_conv (MSE=0.12) ← 深度估计最敏感!
# 2. fpn.p3_conv (MSE=0.08)
# 3. bev_encoder.layer1 (MSE=0.05)
# 4. detection_head.cls_conv (MSE=0.04)
# 5. backbone.stem (MSE=0.03)

# 策略: 敏感层保持 FP16, 其余 INT8 → 精度损失 <0.5 NDS
```

> [!warning] 为什么 depth_net 最敏感？（重要）
> 深度估计层输出**概率分布**（128 个 bin 的 softmax），INT8 量化会"压平"分布细节——峰值不清晰，深度估计就歪了（[[BEVDet与BEVDepth]] 讲过"深度错则全错"）。**所以敏感层（depth net）保持 FP16，其余 INT8**——这是"混合精度部署"的标准做法，精度损失从 2% 降到 <0.5%。

### 2.3 自定义 Plugin — BEVPoolv2 for TensorRT

```cpp
// BEVPoolv2 不是标准 ONNX op → 需要自定义 TRT plugin
class BEVPoolv2Plugin : public IPluginV2DynamicExt {
    int enqueue(const PluginTensorDesc* inputs,
                const PluginTensorDesc* outputs,
                const void* const* buffers,
                cudaStream_t stream) override {
        // 输入: frustum_features, depth_distribution, cam_params
        // 输出: bev_features

        // CUDA kernel: 加速 Voxel Pooling
        bev_pool_v2_kernel<<<grid, block, 0, stream>>>(
            (const float*)buffers[0],  // frustum features
            (const float*)buffers[1],  // depth distribution
            (const int*)buffers[2],    // precomputed BEV indices
            (float*)buffers[3]         // output BEV features
        );
        return 0;
    }
};

// 实测: custom plugin BEVPoolv2 → 18ms → 6ms (-12ms)
```

> [!note] Plugin 的意义：**让"非标准算子"也能被 TensorRT 加速**
> BEVPoolv2（[[BEVDet与BEVDepth]] 第四节）是自定义 CUDA kernel，不是 ONNX 标准算子——TensorRT 不认识它。Plugin 就是"告诉 TensorRT 这个算子怎么跑"的接口。**这是 BEVFormer 部署难（Deformable Attention 要写 plugin）vs BEVDet 部署易（纯标准算子）的根源**——再次印证"算子类型决定部署成本"。

## 三、推理优化技巧速查表

| 技巧 | 加速比 | 精度损失 | 适用场景 |
|------|:-----:|:------:|------|
| **FP16** | 1.5-2× | <0.1% | 默认开启 |
| **INT8 (PTQ)** | 2-3× | 0.5-2% | 大部分层 |
| **INT8 (QAT)** | 2-3× | <0.5% | 精度敏感场景 |
| **TensorRT engine** | 1.5-3× | 0 | 必备 |
| **Layer Fusion (Conv+BN+ReLU)** | 1.2× | 0 | 自动 |
| **Kernel Auto-tuning** | 1.1-1.5× | 0 | 自动 |
| **降低分辨率** | 2-4× | 1-3 NDS | 紧急降延迟 |
| **轻量 Backbone** | 2-3× | 1-2 NDS | 端侧部署 |
| **去掉 NMS (center-based)** | +10% FPS | 0 | 无条件推荐 |

> [!note] 读表的"使用顺序"
> ① **零成本先做**：TensorRT engine + Layer Fusion（自动）+ 去 NMS（center-based head）；② **低成本**：FP16（默认）；③ **有取舍**：INT8 量化（先 PTQ 试，敏感层混合精度）；④ **伤筋动骨**：降分辨率、轻量 backbone（精度损失大，最后才动）。**顺序 = 从"无损"到"有损"，逐级往下**。

## 四、面试官追问

### Q1: 你说 TensorRT 量化后某层精度损失大，怎么修复？

三阶修复方案:
1. **Layer-wise partial quantization**: 那层保持 FP16 → 对总延迟影响 <5%
2. **QAT (Quantization-Aware Training)**: 训练时模拟 INT8 量化 → 模型主动适应 → 精度恢复
3. **重新设计该层**: 如果该层对量化本身就不友好（如 depth softmax）→ 换一个量化友好的替代设计

> [!note] 回答框架：**从"部署侧"到"训练侧"到"设计侧"**
> ① 部署侧：敏感层保持 FP16（最快，损失可接受）；② 训练侧：QAT 让模型"学会被量化"（训练时模拟 INT8，精度恢复最好）；③ 设计侧：换掉量化不友好的算子（如 depth softmax → 量化友好的变体）。**三级递进：先改部署配置，再改训练方式，最后改模型设计。**

### Q2: 多模型 Pipeline（检测→跟踪→预测）的延迟怎么优化？

1. **Batching**: 多个模型共用 Backbone (multi-task head) → 省掉 3 个 Backbone 的推理
2. **Pipeline Parallelism**: GPU 跑检测时 CPU 做跟踪 → 重叠
3. **模型合并**: 检测+跟踪一个模型出两结果 → 省掉跟踪推理 (如 CenterTrack 风格)
4. **异步推理**: 检测每帧跑，跟踪每 2 帧跑，预测每 5 帧跑 → 帧率解耦

> [!note] 核心思想：**消除"串行等待"**
> 多模型串联的延迟 = 各模型延迟之和。优化方向：① 共享（共用一个 backbone）；② 重叠（CPU/GPU 并行）；③ 合并（一个模型多输出）；④ 降频（不是每个任务都要每帧跑——跟踪 2 帧一次、预测 5 帧一次够用）。**"帧率解耦"是最容易被忽视的大招**：感知 30Hz 不代表规划也要 30Hz。

### Q3: 如果模型在 GPU 上延迟满足要求，但 CPU 做后处理的 NMS 拖后腿，怎么办？

1. GPU 端 NMS (torchvision.ops.nms / custom CUDA kernel)
2. Center-based head (不需要 NMS!)
3. 如果没有 GPU 可用: 降采样 (只对 top-K proposals 做 NMS)
4. 近似 NMS: 将 proposals 分组到 grid → 每组独立 NMS → 并行化

> [!note] 最佳答案先说"根治"：**Center-based head 根本不需要 NMS**（[[BEVDet与BEVDepth]] 提过）——这是设计层面的根治。其次是工程方案（GPU 端 NMS/并行 NMS）。**回答顺序：设计根治 > 工程优化 > 兜底降级**。

## 五、常见误区速查

> [!warning] 新手最常踩的坑
> 1. **不测就优化**——凭感觉砍模块，不如先 profiler 测出真实占比（37% 的 Backbone 和 5% 的 NMS 收益差 7 倍）。
> 2. **以为 INT8 是"免费的 2-3 倍加速"**——敏感层（depth net）会掉精度，必须逐层分析 + 混合精度。
> 3. **以为 TensorRT 万能**——Deformable Attention/BEVPool 等非标准算子要写 plugin，否则要么不支持要么巨慢（这是 BEVFormer 部署难的原因）。
> 4. **只优化模型推理，忽略整条链路**——固定开销 75ms 占一半预算，传感器/规划/控制也是可优化对象。
> 5. **忽略"帧率解耦"**——不是所有任务都要每帧跑，异步/降频能白捡大量延迟。

## ✅ 检验自己（自测题）

> [!question] Q1：面对"模型 100ms、总预算 150ms"你怎么拆解并给出方案？
> 提示：先算固定开销，再分模块，再砍大头。

> [!success]- 参考答案
> ① 先算固定开销（传感器 10 + 传输 5 + 预处理 5 + 后处理 5 + 跟踪 5 + 预测 20 + 规划 20 + 控制 5 = 75ms）→ 模型预算 75ms，当前 100ms 超 25ms；② 用 profiler 拆模型（Backbone 37% / View Transform 24% / BEV Encoder 16%）；③ 砍 25ms：降分辨率 1600×900→800×450（-18ms，最安全）+ 去 NMS 用 CenterPoint head（-4ms，几乎无损）≈ 42ms 达标；④ 精度损失 NDS -2.0 用更好 backbone（EfficientNet-B3）补偿约 1.0。**框架：算预算 → 测占比 → 组合拳砍 → 补偿精度。**

> [!question] Q2：INT8 量化后某层精度损失大，三阶修复方案是什么？
> 提示：部署侧 → 训练侧 → 设计侧。

> [!success]- 参考答案
> ① 部署侧：该层保持 FP16（layer-wise partial quantization，延迟影响 <5%）；② 训练侧：QAT 量化感知训练（训练时模拟 INT8，模型主动适应，精度恢复最好）；③ 设计侧：更换量化不友好的算子设计（如 depth softmax）。由浅入深：先改配置，再改训练，最后改设计。

> [!question] Q3：为什么 depth_net（深度估计层）对 INT8 量化最敏感？
> 提示：softmax 分布被压平。

> [!success]- 参考答案
> 深度估计层输出的是 128 个 bin 的概率分布（softmax），INT8 量化会压平分布的细节——峰值不清晰，深度估计就偏了，而 LSS 范式"深度错则全错"（级联误差）。所以典型做法：depth_net 保持 FP16，其余层 INT8，混合精度部署精度损失从 ~2% 降到 <0.5%。

> [!question] Q4：多模型 pipeline（检测→跟踪→预测）延迟怎么优化？哪个是大招？
> 提示：共享/重叠/合并/降频。

> [!success]- 参考答案
> ① Batching：多个任务共用 Backbone（multi-task head）；② Pipeline Parallelism：GPU 算检测、CPU 做跟踪（重叠）；③ 模型合并：检测+跟踪一个模型（CenterTrack 风格）；④ 异步/降频：检测每帧、跟踪每 2 帧、预测每 5 帧（帧率解耦）。大招是"帧率解耦"——不是所有任务都要每帧跑，感知 30Hz 不代表规划也要 30Hz，能白捡大量延迟。

> [!question] Q5：为什么"先测后砍"是延迟优化的第一原则？
> 提示：二八法则。

> [!success]- 参考答案
> 凭感觉优化可能把精力花在 5% 的模块上（如 NMS），而真实瓶颈是 37% 的 Backbone。先用 profiler/nsys 测出每个模块的真实耗时占比，再按占比排序优化——同样精力，砍 37% 的模块收益是砍 5% 模块的 7 倍。**"测占比 → 砍大头 → 组合拳"是延迟优化的标准方法论。**

## 🛠 动手练习

### 练习 1：延迟预算实战（30 分钟）

给定：传感器 12ms + 预处理 6ms + 后处理 6ms + 跟踪 8ms + 预测 25ms + 规划 25ms + 控制 6ms，总预算 180ms。
1. 算固定开销和模型推理预算。
2. 模型当前 95ms，超出多少？需要砍多少？
3. 设计一个方案（从"无损优先"到"有损"排列你的手段）。

> [!tip] 做完后自问
> ① 固定开销里哪项最大？（预测 25ms——规划侧也可以优化）② 如果传感器换成更快的（曝光 12→8ms），模型预算变多少？——**固定开销也是可优化的，不要只盯模型。**

### 练习 2：用 trtexec 跑一次 TensorRT 转换（可选，1-2 天）

如果你有 NVIDIA GPU 和 TensorRT（或用 [[本地训练方案]] 的环境）：
1. 导出任意小模型为 ONNX（torch.onnx.export）。
2. 用 trtexec 转 FP16 engine，对比 FP32 的推理时间。
3. 尝试 INT8 校准（需要校准数据），观察精度变化。

> [!warning] 环境提示
> TensorRT 对 GPU 型号和 CUDA 版本敏感。如果环境受限，可以只做 ONNX 导出 + 用 onnxruntime 对比精度——先跑通"PyTorch → ONNX"这一步，TensorRT 部分等有 GPU 环境再补。
